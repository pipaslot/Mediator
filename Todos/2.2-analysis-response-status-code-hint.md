# HTTP status code hint na kontextu — analýza proveditelnosti

**Role:** Architecture advisor
**Účel:** Posoudit realizovatelnost, rizika a přínosy zavedení mechanismu, kterým middleware/handler ovlivní konkrétní HTTP status kód odpovědi (400, 401, 409...), aniž by middleware přímo sahal na `HttpContext.Response.StatusCode`, a aniž by tím vznikal stejný "root vs. nested" bug jako u přímého zápisu do response body.

Vychází z položky **"TODO : HTTP status code hint on context"** v [2.0-todo-feature-requests.md](2.0-todo-feature-requests.md) a z konkrétního, dnes existujícího vzoru v `ValidationMediatorMiddleware` (mimo tento repozitář), který přesně demonstruje popsaný anti-pattern.

**Konsolidace:** Tato analýza je sesterský dokument k [2.1-analysis-nested-call-http-direct-response-write.md](2.1-analysis-nested-call-http-direct-response-write.md) — řeší strukturálně stejnou třídu problému ("root vs. nested" leak do sdíleného `HttpContext`), jen na úrovni status kódu místo těla odpovědi. Kde je to relevantní, znovupoužívá stejné pojmy a stavební kameny místo jejich opakování.

---

## 1. Shrnutí problému

Dodaný příklad `ValidationMediatorMiddleware` (mimo tento repozitář) dnes dělá přesně to, před čím TODO varuje:

```csharp
public async Task Invoke(MediatorContext context, MiddlewareDelegate next)
{
    var errors = await _validationProvider.Validate(context.Action);
    if (errors.Any())
    {
        context.Status = ExecutionStatus.Failed;
        context.AddResult(new Notification { ... Type = NotificationType.Error });

        var httpContext = _httpContextAccessor.HttpContext;
        if (httpContext == null) return;
        httpContext.Response.StatusCode = 400;   // <- přímý zápis, bez ohledu na nesting
    }
    else
    {
        await next(context);
    }
}
```

Na rozdíl od `ExportStreamHandler`/`DemoDownloadHandler` (řešeno v 2.1) jde o **middleware**, ne o handler — a middleware se typicky registruje přes `UseWhen`/`Use<T>()` napříč **všemi** akcemi splňujícími podmínku, root i vnořenými. To dělá pravděpodobnost nested-call bugu vyšší než u jednotlivého handleru: stačí, aby akce, která dnes prochází touto validací, byla i jen jednou zavolána jako vnořené volání (`mediator.Execute(subAction)` uvnitř jiného handleru), a přímý zápis do `HttpContext.Response.StatusCode` okamžitě přepíše status kód **celé** HTTP odpovědi — bez ohledu na to, zda rodičovský handler chybu zachytí, zotaví se z ní, nebo ji sám nahradí jiným výsledkem.

## 2. Co knihovna dnes umí (a co ne)

| Stavební kámen | Kde | Poznámka |
|---|---|---|
| `MediatorContext.IsNested` / `Depth` | `Pipaslot.Mediator/Middlewares/MediatorContext.cs:88-93` | Stejný mechanismus jako v 2.1 — dostupný, HTTP-agnostický, dnešní `ValidationMediatorMiddleware` ho nepoužívá. |
| `MediatorContext.Features` (`IFeatureCollection`) | `Pipaslot.Mediator/Middlewares/MediatorContext.cs:59-73`, `Middlewares/Features/` | Existující, obecný mechanismus **přesně pro tento účel** — CLAUDE.md ho popisuje jako "ASP.NET Core-style extensible per-request feature bag" určený "for sharing data between middleware" (přidáno v 7.5.0). Dnes ho používá `MiddlewareParametersFeature` (core) a `MediatorHttpContextFeature` (`Pipaslot.Mediator.Http/Internal/`, HTTP-specifická feature žijící mimo core). |
| Každý (i vnořený) `MediatorContext` je nezávislý | `Pipaslot.Mediator/Mediator.cs:185-188` (`CreateContext`) | **Klíčové zjištění pro tuto analýzu:** `CreateContext` vytváří pro každé volání (root i nested) čerstvý `MediatorContext` s `defaultFeatures: null` — `Features` vnořeného kontextu **nejsou nijak zřetězeny/zděděné** od rodiče. Nic z toho, co middleware zapíše do `context.Features` ve vnořeném volání, se samo od sebe neobjeví v `Features` rodičovského/root kontextu. Stejná strukturální izolace, jakou 2.1 popisuje pro `Results` (§4) — jen o úroveň přísnější, protože pro `Features` dnes neexistuje ani manuální "forward jako svůj vlastní" cesta, kterou `Results` mají. |
| `NotificationPropagationMiddleware` | `Pipaslot.Mediator/Middlewares/NotificationPropagationMiddleware.cs` | **Přesný precedent pro potřebný propagační mechanismus.** Vkládá se do pipeline jen když `context.IsNested` (`Mediator.GetPipeline`, `hasParentContext` parametr), a po doběhnutí `next(context)` zkopíruje `Notification` výsledky (mimo ty se `StopPropagation=true`) do `context.ParentContexts.First()` (= nejbližší rodič, ne nutně root — díky vkládání middlewaru na každé úrovni nestingu se propagace řetězí krok po kroku, dokud nedorazí do root kontextu). `AddResults` → `AddResult` navíc sama nastaví `ParentContext.Status = Failed`, pokud propagovaná notifikace `IsError()`. |
| `ServerMediatorOptions.ErrorHttpStatusCode` + dnešní status-code logika | `Pipaslot.Mediator.Http/MediatorMiddleware.cs:43-47` | `if (context.Response.StatusCode == 200 && mediatorResponse.Failure) context.Response.StatusCode = option.ErrorHttpStatusCode;` — tedy **jen** binární "selhalo/neselhalo" → jeden nakonfigurovaný kód (500 default). Přepíše se pouze pokud je kód stále 200 — což je přesně ten mechanismus, který dnešní přímý zápis z `ValidationMediatorMiddleware` (nechtěně) obchází a nahrazuje. |
| Wiki dokumentuje dnešní anti-pattern jako **záměrné** chování | `docs/wiki/8.-HTTP-transport-and-configuration-for-Client-Server-usage.md:91-92` | *"If a middleware already changed the status code (e.g. to signal a validation error), that value is preserved and `ErrorHttpStatusCode` is not applied."* — knihovna dnes ne že jen toleruje přímý zápis do `HttpContext` z middlewaru, ale své vlastní chování (nepřepisovat už změněný kód) staví na tom, že middlewary to dělají. To je přesně vzor `ValidationMediatorMiddleware`. Bez migrace by zavedení hintu tuto větu ve wiki znejasnilo/rozporovalo. |

Závěr: na rozdíl od `IMediatorHttpResult` (2.1), kde chyběl jen jeden nový kontrakt a propagace se vyřešila "zadarmo" (protože `Results` se nepropagují automaticky), zde už **existuje hotový propagační mechanismus přesně pro tento tvar problému** (`NotificationPropagationMiddleware`) — jde tedy spíš o "znovupoužij/napodob", než o "navrhni od nuly".

## 3. Reálně existující riziko v dnešním chování (ne jen hypotéza)

Konkrétní řetězec s dodaným kódem:

1. Akce `A` je zavolána jako kořenová HTTP akce. Handler `A` interně zavolá `mediator.Execute(actionB)` (vnořené volání, `Depth == 2`) a **zachytí/zotaví se** z případné chyby `actionB` (typický důvod, proč se nested volání vůbec dělá — např. "zkus dávkově, při první chybě přeskoč a pokračuj dál").
2. `ValidationMediatorMiddleware` je registrován přes `UseWhen(...)` napříč akcemi včetně `actionB`. `actionB` selže validací.
3. Middleware nastaví `context.Status = Failed` **na kontextu `actionB`** (správně, lokálně) — ale zároveň napíše `httpContext.Response.StatusCode = 400` **přímo na sdílený `HttpContext`**, bez ohledu na to, že `actionB` je vnořené volání.
4. Handler `A` chybu `actionB` zachytí a i tak dokončí úspěšně — `context.Status` pro `A` zůstane `Succeeded`.
5. `MediatorMiddleware.Invoke` po doběhnutí `mediator.Execute(actionA, ...)` uvidí `mediatorResponse.Failure == false`, takže se do status-code větve (`Pipaslot.Mediator.Http/MediatorMiddleware.cs:43-47`) vůbec nedostane — ale to je jedno, `context.Response.StatusCode` je už `400` z kroku 3, natrvalo, protože v `MediatorMiddleware` nic status kód nikdy neresetuje na 200.

Výsledkem je klient dostane `400 Bad Request` pro **úspěšnou** odpověď — přesně ten scénář, který "Hard requirement (decided)" v [2.0](2.0-todo-feature-requests.md) explicitně pojmenovává jako nutnou podmínku k vyřešení, jen zde doložený na reálném, dodaném kódu místo hypotézy.

## 4. Návrh řešení — tři nezávislé stavební bloky

### Blok 1 — Kde hint uložit: `MediatorContext.ResponseStatusCodeHint` (core) vs. `IFeatureCollection` (Http-specifická feature)

Původní návrh v [2.0](2.0-todo-feature-requests.md) navrhuje `int? ResponseStatusCodeHint` přímo jako novou public property na `MediatorContext` (core). Alternativa, kterou tato analýza doplňuje: **HTTP-specifická feature** (`ResponseStatusCodeHintFeature`) uložená přes už existující `context.Features`, žijící v `Pipaslot.Mediator.Http` — analogicky k `MediatorHttpContextFeature`.

| | Core property (`MediatorContext.ResponseStatusCodeHint`) | Feature (`context.Features.Set(new ResponseStatusCodeHintFeature(400))`) |
|---|---|---|
| Kam patří | `Pipaslot.Mediator` (core, multi-target net6.0–net10.0, HTTP-agnostický balíček) | `Pipaslot.Mediator.Http` (žádná core změna) |
| Konzistence s architekturou | "HTTP status code" je HTTP doménový pojem zapsaný natrvalo do transport-agnostického typu, i když je datový typ jen `int?` | Přesně účel, pro který `Features` byly zavedeny (CLAUDE.md: "sharing data between middleware"); precedent `MediatorHttpContextFeature` už dnes žije mimo core ze stejného důvodu |
| Riziko pro budoucí non-HTTP transport | `MediatorContext` by natrvalo nesl vlastnost bez smyslu mimo HTTP | Žádné — core zůstává nedotčen |
| Ergonomie pro konzumenta | `context.ResponseStatusCodeHint = 400;` — nejkratší zápis | Vyžaduje extension metodu v `Pipaslot.Mediator.Http` (`context.SetResponseStatusCodeHint(400)`), ale zápis je stejně krátký pro konzumenta |
| Náklad na zavedení | Nová veřejná property v hot-path core třídě, byť aditivní | Nová třída v `.Http`, žádná core změna |

**Doporučení této analýzy:** Feature. Přímo naplňuje důvod, proč `Features` v knihovně existují, nemění core surface, a je konzistentní s tím, jak byl `IMediatorHttpResult` (2.1) záměrně udržen mimo core. Je to ale změna oproti doslovnému znění TODO v 2.0 — otevřená otázka k potvrzení, ne rozhodnutí učiněné touto analýzou.

### Blok 2 — Propagace mezi úrovněmi nestingu: nový middleware analogický `NotificationPropagationMiddleware`

Protože `Features` (blok 1) jsou dnes striktně per-kontext bez jakéhokoliv sdílení (viz tabulka v §2, řádek "Každý kontext je nezávislý"), hint nastavený ve vnořeném volání **strukturálně nemůže** uniknout do rodiče, dokud to něco výslovně neudělá — čímž je "Hard requirement" z 2.0 (hint umírá s vnořeným kontextem, pokud ho rodič výslovně nepřevezme) splněn jako výchozí stav zdarma, stejně jako u `IMediatorHttpResult` v 2.1.

Pro *žádoucí* případy (validace vnořené akce má ovlivnit HTTP status kód celého požadavku, i když handler chybu jinak zpracuje jako `Notification`) je potřeba explicitní krok navíc — přesně vzor `NotificationPropagationMiddleware`:

```csharp
internal class ResponseStatusCodeHintPropagationMiddleware : IMediatorMiddleware
{
    public async Task Invoke(MediatorContext context, MiddlewareDelegate next)
    {
        await next(context).ConfigureAwait(false);

        if (context.IsNested)
        {
            var hint = context.Features.Get<ResponseStatusCodeHintFeature>();
            if (hint is not null)
            {
                var parent = context.ParentContexts.First();
                // kolizní pravidlo zde — viz §5.1
            }
        }
    }
}
```

Vkládal by se do pipeline stejnou podmínkou jako `NotificationPropagationMiddleware` (`hasParentContext: context.IsNested` v `Mediator.GetPipeline`), takže by se řetězil přes libovolný počet úrovní nestingu automaticky.

### Blok 3 — Aplikace na `HttpContext` jen z root kontextu

Analogicky k `IMediatorHttpResult` (2.1 §4) a k dnešnímu `ErrorHttpStatusCode` bloku — pouze `Pipaslot.Mediator.Http.MediatorMiddleware`, po doběhnutí celé root pipeline, s `HasStarted` guardem:

```csharp
var hint = rootContext.Features.Get<ResponseStatusCodeHintFeature>();
if (hint is { } h && !context.Response.HasStarted)
{
    context.Response.StatusCode = h.StatusCode;
}
else if (context.Response.StatusCode == (int)HttpStatusCode.OK && mediatorResponse.Failure)
{
    context.Response.StatusCode = option.ErrorHttpStatusCode; // dnešní fallback beze změny
}
```

Pořadí vůči `IMediatorHttpResult` bloku (`Pipaslot.Mediator.Http/MediatorMiddleware.cs:31-41`) je potřeba rozhodnout — pravděpodobně hint aplikovat jen ve větvi, kde se nakonec píše JSON (pokud `IMediatorHttpResult` převzal odpověď, hint na status kód už nedává smysl, protože `ApplyAsync` má nad `HttpContext` plnou kontrolu).

## 5. Otevřené otázky

### 5.1 Kolizní pravidlo (nerozhodnuto v 2.0, stále nerozhodnuto zde)

Když stejná nebo různé úrovně nestingu nastaví různé hinty, co má vyhrát? Tři reálné možnosti, žádná zjevně "ta jediná správná":

- **Last-writer-wins** (poslední zápis na dané úrovni/rodiči přepíše předchozí) — nejjednodušší, ale pořadí zpracování vnořených volání je implementační detail, na kterém by chování nemělo záviset.
- **Severity/prioritní pravidlo** (např. `401 > 403 > 400 > 409`, konfigurovatelná tabulka) — deterministické a nezávislé na pořadí, ale je to nová věc k nakonfigurování/dokumentování a přidává překvapivou komplexitu pro jednoduchý případ jednoho validačního middlewaru.
- **Throw při kolizi** (analogie k právě implementovanému `IMediatorHttpResult` — 2.1, kde více než jeden výsledek v `Results` nyní vede k `MediatorHttpException` místo tichého výběru prvního) — **pozor, není to přímo přenositelný precedent**: u `IMediatorHttpResult` je přítomnost dvou konfliktních výsledků skutečně vždy chyba konfigurace (dvě těla odpovědi nelze smysluplně sloučit). U status kódů je běžné, že různé části jednoho požadavku (více nezávislých vnořených volání ve stejném rodiči, např. dávkové zpracování) mohou legitimně hlásit různé chybové kódy současně — throw by tu mohl trestat zcela normální, ne-chybový stav.

Doporučení k dalšímu rozhodnutí (ne rozhodnutí samo): severity-based pravidlo s rozumným defaultem (např. numericky nejvyšší 4xx/5xx kód vyhrává, protože typicky odpovídá nejzávažnějšímu problému), s možností přepsat konfigurací — ale toto vyžaduje samostatné potvrzení, přesně jak 2.0 už predikuje ("blocked on the recovery-semantics requirement" a "could not be decided unambiguously").

Zpětná vazba od autora:
nejlogičtější je vůbec nepropagovat http status ze vnořených volání, jelikož nejsou vlastníkem http contextu a tab jej neměly být schopny ani měnit. učelem je umožnit vytvařed akci/handler, jež lze volat z klienta, ale také umožnit vnořené vlolání a tím jen přístup k výsledku. 
V tomto případě se nastaví stav MediatorContext na failed, pošle se notifikace, která by neměla být propagovana dál (StopPropagation = true) z validačního middleware )můžeme poslytnout helper nebo doporučeni v dokumentaci) a následná chyba se bud projevi jako Success/Failed status mediator volání, nebo bude vyhozeno jako vyjímka v případě unhandled metod.

### 5.2 Blok 1 (core property vs. Feature) je změna oproti doslovnému zadání v 2.0

Tato analýza doporučuje Feature místo core property (viz §4, Blok 1) — je to odchylka od TODO textu v 2.0, ne jeho doslovná realizace. Potřebuje explicitní potvrzení/zamítnutí, ne tichou náhradu při implementaci.

### 5.3 Migrace dnešní zdokumentované chování

`docs/wiki/8.-HTTP-transport-and-configuration-for-Client-Server-usage.md:91-92` dnes popisuje přímý zápis do `HttpContext.Response.StatusCode` z middlewaru jako podporovaný vzor ("If a middleware already changed the status code..."). Zavedení hintu by tuto pasáž muselo nahradit/doplnit tak, aby nedoporučovala anti-pattern, který právě tento TODO odstraňuje — analogicky k tomu, jak 2.1 upravila `docs/wiki/9.3...md`, aby vedle sebe měla doporučený a alternativní (accept guard) postup.

### 5.4 Vztah k `IMediatorHttpResult` (2.1)

Sdílí stejný integrační bod v `MediatorMiddleware.Invoke` (viz Blok 3) — pořadí zpracování obou mechanismů je potřeba rozhodnout společně, ne odděleně (stejná otevřená otázka byla zapsaná i v 2.1 §7 bod 8, tehdy zůstala nerozhodnuta ve prospěch "dva nezávislé mechanismy").

## 6. Reálné přínosy

- Odstraňuje reálně existující, dnes demonstrovaný nested-call bug (§3), stejné třídy jako `IMediatorHttpResult` řešil pro tělo odpovědi — jen pro status kód.
- Znovupoužívá už otestovaný, funkční propagační vzor (`NotificationPropagationMiddleware`) místo návrhu nového mechanismu od nuly — nižší implementační riziko než u 2.1's Varianty D, která byla zcela nový kontrakt.
- Sjednocuje architekturu: pokud se přijme Blok 1 jako Feature, `Pipaslot.Mediator` zůstává 100% HTTP-agnostický i po zavedení této funkce, beze změny core veřejného API.

## 7. Doporučení

1. **Okamžitá mitigace pro `ValidationMediatorMiddleware` (mimo tento repozitář), nezávislá na knihovně:** guard `if (contextAccessor.Context?.IsNested == true) { /* nezapisuj do HttpContext, jen nastav Status/Notification */ }` — dostupné ihned, stejná okamžitá oprava, jakou 2.1 doporučila pro `ExportStreamHandler`.
2. **Navazující design session** (mimo scope této analýzy) musí rozhodnout §5.1 (kolizní pravidlo) a §5.2 (core property vs. Feature) — obě jsou behaviorální/architektonická rozhodnutí, ne technické detaily, a nemají jednoznačně "správnou" odpověď odvoditelnou jen z kódu.
3. Při implementaci současně aktualizovat `docs/wiki/8.-HTTP-transport-and-configuration-for-Client-Server-usage.md:91-92` (viz §5.3) a přidat changelog bullet do `Release-notes-and-breaking-changes.md` (per CLAUDE.md).
