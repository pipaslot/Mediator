# Issue: `MediatorExecutionException` conflates "already-handled business error" with genuine framework/configuration failures

**Status:** Root cause for the approved redesign in [1.2-error-handling-design-decision.md](1.2-error-handling-design-decision.md). See also [1.1-analysis-mediatr-error-handling-comparison.md](1.1-analysis-mediatr-error-handling-comparison.md) for the MediatR-comparison research that fed into that decision.

## Summary

`Pipaslot.Mediator`'s `ExecuteUnhandled<TResult>` / `DispatchUnhandled` throw the **same exception type** (`MediatorExecutionException`) for three qualitatively different situations:

1. A handler or middleware legitimately failed and already recorded a translated, user-facing error message on the context (`ExecutionStatus.Failed`) — expected, "business as usual" outcome.
2. No handler was found for the action at all (`CreateForNoHandler`) — a deployment/registration bug.
3. The pipeline succeeded but a custom `IExecutionMiddleware`/middleware bug failed to attach the expected result type (`CreateForMissingResult`) — a code bug in a custom middleware.

Because all three surface as the same `MediatorExecutionException` type with no discriminator other than the free-text `Message`, **consuming code cannot reliably tell them apart** without string-matching the message — which is fragile and exactly what we are trying to avoid (see existing `TODO` in our own `ErrorHandlingMiddleware`, quoted below).

This was discovered while auditing why a nested mediator call (`Dispatch` → handler → `mediator.ExecuteUnhandled(...)`) can cause an **expected, already-translated business error to be misreported as an "UNEXPECTED" system error** (spurious error-level log entries + error notification emails to support), even though the failure was fully handled and translated at the point it occurred.

## Reproduction / mechanism

Repo: `Pipaslot.Mediator` (this repository). Consuming app: internal `FIT.WebApi` (external, not part of this repo — code excerpt below is provided for context only).

Setup:
- A global `ErrorHandlingMiddleware` is registered in the mediator pipeline. It wraps `next(context)` in a big `try/catch`, translates known exception types into user-facing messages via `context.AddError(...)`, and **does not rethrow** for the "expected" branches (see excerpt below). This is the ASP.NET-Core-style "terminal error handler" pattern.
- A handler for action A performs a **nested** mediator call using `mediator.ExecuteUnhandled(actionB)` (chosen specifically so failures surface as C# exceptions instead of having to check `context.Status` manually).
- The handler for action A does **not** currently catch `MediatorExecutionException` around that nested call (see the team's own `TODO` below — this is a known, intentional gap for now).

Step by step:

1. Handler for action B throws a normal, expected exception (e.g. `NotFoundException`, `FluentValidation.ValidationException`).
2. The **inner** instance of `ErrorHandlingMiddleware` (it runs for every pipeline execution, including nested ones) catches it, translates it to a localized message, calls `context.AddError(translatedMessage)`, and returns **without rethrowing**.
3. Because this is a nested call, `Pipaslot.Mediator` automatically inserts `NotificationPropagationMiddleware` as the outermost middleware of the inner pipeline (`Pipaslot.Mediator/Mediator.cs`, `GetPipeline`, ~line 140-148). Its `Invoke` is:
   ```csharp
   public async Task Invoke(MediatorContext context, MiddlewareDelegate next)
   {
       await next(context).ConfigureAwait(false);   // only reaches the code below if next() did NOT throw
       var parentContext = context.ParentContexts.FirstOrDefault();
       if (parentContext is not null)
       {
           var notifications = context.Results.Where(r => r is Notification n && !n.StopPropagation);
           parentContext.AddResults(notifications);
       }
   }
   ```
   (`Pipaslot.Mediator/Middlewares/NotificationPropagationMiddleware.cs`)

   Since step 2 did **not** let an exception escape, `next(context)` returns normally here, so the translated notification **is** propagated into the parent (outer) context's `Results` — this happens *before* `ExecuteUnhandled` ever inspects the status.
4. Back in `ExecuteUnhandled` (`Pipaslot.Mediator/Mediator.cs`, ~line 99-135): the pipeline finished with `context.Status != Succeeded`, so it throws:
   ```csharp
   throw MediatorExecutionException.CreateForUnhandledError(context);
   ```
   whose message is a generic wrapper (`Pipaslot.Mediator/MediatorExecutionException.cs`, line 39-44):
   ```csharp
   $"Handler or middlewares set the ExecutionStatus to {ExecutionStatus.Failed}. To prevent this exception, user methods Mediator.Dispatch or Mediator.Execute instead. Error messages: [{errors}]"
   ```
   (`errors` is the already-translated business message from step 2, embedded inside this technical sentence.)
5. The calling handler for action A does not catch this (see TODO below), so it bubbles out through `RequestHandlerExecutor`/`MessageHandlerExecutor` (which only do `context.Status = Failed; throw;`, no message rewriting) into the **outer** pipeline.
6. The **outer** instance of `ErrorHandlingMiddleware` catches it in its final, generic `catch (Exception ex)` block. `MediatorExecutionException` is not in the "acceptable" type whitelist:
   ```csharp
   if (ex is AuthorizationException
       || ex is Pipaslot.Mediator.Authorization.AuthorizationException
       || ex is AuthenticationException
       || ex is ValidationException
       || ex is FluentValidation.ValidationException
       || ex is OperationCanceledException
       || ex is WorkflowException)
   {
       context.AddError(ex.Message);
       // logged as ACCEPTABLE
   }
   else
   {
       context.AddError(ex.Message.Truncate(500));
       Log(LogLevel.Error, ex, "UNEXPECTED", context.ActionIdentifier, context.Action);
       await SendErrorEmail(serviceScopeFactory, ex, context.ActionIdentifier); // <-- spurious alert
   }
   ```
   → falls into the `else` branch: logged as `UNEXPECTED` at `Error` level, and an error email is sent to support/ops — **for what was actually a fully-handled, expected business failure**.

7. Final `context.Results` for the top-level `Dispatch` call end up containing **both** the original translated business notification (propagated in step 3) **and** the generic technical wrapper text (added in step 6), and the app has generated a false-positive incident alert.

### Existing evidence in the codebase that this is a known pain point

The consuming middleware already has a `TODO` acknowledging the string-matching workaround this gap forces:

```csharp
// TODO: Once we upgrade to mediator 8 then for nested calls: stop saving errors in the context as string
// message, but re-throw the exception, so we can use ExecuteUnhandled and catch the exceptions in the
// flow directly (and avoid message matching via string.Contains function)
```

And `Pipaslot.Mediator`'s own demo shows the intended pattern of catching `MediatorExecutionException` explicitly around a nested call (`Demo/Server/Handlers/Playground/CascadingToAnotherFailingRequestMessageHandler.cs`), but that only works if every call site remembers to add this try/catch — there is currently no type-level way to enforce or simplify it.

## Why the naive fix is unsafe

The obvious "quick fix" — add `MediatorExecutionException` to the outer `ErrorHandlingMiddleware`'s acceptable-exception whitelist — was considered and **rejected**, because `MediatorExecutionException` is also thrown for cases that are *not* expected business failures and genuinely should be logged as `UNEXPECTED` / alert support:

- `MediatorExecutionException.CreateForNoHandler(...)` — no handler is registered for an action at all. This is a deployment/DI-registration bug, low probability but real (e.g. missed `AddHandlersFromAssembly` call, typo in a conditional registration, etc.).
- `MediatorExecutionException.CreateForMissingResult(...)` — pipeline reported success but a custom middleware bug failed to attach the expected result object to the context.

Whitelisting the type wholesale would silently swallow (from an alerting perspective) exactly the class of *critical, unexpected* runtime failures the middleware exists to catch. The probability of hitting these two cases in production is low, but "low but not zero, and currently indistinguishable from a routine validation failure" is not an acceptable trade-off for turning off alerting.

## Impact

- **False-positive incident noise**: every nested `ExecuteUnhandled`/`DispatchUnhandled` call whose inner pipeline fails "normally" (validation, not-found, business rule) and is not explicitly caught by the calling handler currently triggers an `UNEXPECTED`-level log entry and an error email to support, unless the calling handler remembers to catch `MediatorExecutionException` explicitly at every nested call site.
- **Noisy/duplicated user-facing messages**: the final result set can contain both the clean translated message and the generic technical wrapper text, depending on whether/where something re-adds `ex.Message` to the context.
- **No safe, type-based way to fix it**: any attempt to special-case `MediatorExecutionException` in the outer error handler currently also has to swallow real configuration/programming errors (`CreateForNoHandler`, `CreateForMissingResult`), because the library gives no discriminator between them.

## Proposed directions (for evaluation, not prescriptive)

Any of these (or a combination) would let consuming `ErrorHandlingMiddleware`-style code distinguish "already-handled business failure being re-signaled as an exception" from "genuine framework/configuration bug", without string-matching:

1. **Add a discriminator property** to `MediatorExecutionException`, e.g. an enum:
   ```csharp
   public enum MediatorExecutionExceptionReason
   {
       UnhandledError,   // CreateForUnhandledError — status was Failed, already has translated notifications in Response
       NoHandlerFound,   // CreateForNoHandler
       MissingResult     // CreateForMissingResult
   }
   public MediatorExecutionExceptionReason Reason { get; }
   ```
   Consumers could then whitelist only `Reason == UnhandledError` (and rely on `e.Response.Results` for the already-translated notification content instead of re-adding `e.Message`).

2. **Split into distinct exception subtypes**, all still deriving from `MediatorExecutionException` for backward-compatible catch-all handling:
   - `MediatorUnhandledErrorException` (for `CreateForUnhandledError`)
   - `MediatorNoHandlerFoundException` (for `CreateForNoHandler`)
   - `MediatorMissingResultException` (for `CreateForMissingResult`)

3. **Don't let exception-catching middleware apply to nested pipeline executions at all.** `Mediator.cs` already knows, at the point it builds the pipeline, whether the current execution is nested: `ProcessPipeline` computes `contextsCount = mediatorContextAccessor?.Push(context)` and `GetPipeline(action, hasParentContext: contextsCount > 1)` (`Pipaslot.Mediator/Mediator.cs`, lines 152-155). A middleware whose entire purpose is "catch what escapes the handler, translate it, and terminate the exceptional flow" (like `ErrorHandlingMiddleware`) only makes semantic sense at the **root** of a call — once nested, "catching and swallowing" is exactly what re-triggers this whole cascade (translate → propagate → synthesize `CreateForUnhandledError` → get caught *again* by the next level up as if it were new).

   Concretely: give middleware authors a way to say "skip me for nested executions" — e.g. a marker interface (`IRootOnlyMiddleware`) or a `context.ParentContexts.Any()` check inside the middleware itself (already possible today, see `NotificationPropagationMiddleware` doing exactly this check) — so `ErrorHandlingMiddleware` only ever runs once, at the true outer boundary, and nested `ExecuteUnhandled`/`DispatchUnhandled` calls let their raw exceptions propagate straight up to that single boundary instead of being caught-and-rethrown-as-`MediatorExecutionException` at every level.

   This also directly matches how nested calls are *meant* to be consumed: if a caller wants try/catch-style branching, the natural tool is `Execute`/`Dispatch` (which never throw) plus a check on `response.Success`/`context.Status`, not `ExecuteUnhandled` wrapped in a per-call-site `try/catch`. `ExecuteUnhandled`/`DispatchUnhandled` exist for the case where the caller wants failure to propagate as an exception *to its own caller*, unmodified — which is incompatible with an intermediate middleware catching and re-wrapping it at every nesting level.

4. **Move exception translation out of middleware and into `Mediator.cs` itself**, dispatched to registered per-exception-type handler services instead of ad-hoc `try/catch` chains in a middleware. Both `Dispatch` and `Execute` already have a single, well-defined boundary for this — their existing `catch (Exception e)` blocks (`Pipaslot.Mediator/Mediator.cs`, lines 37-41 and 92-96), which currently just do `context.AddError(e.Message)` unconditionally. That boundary could instead resolve a DI-registered collection of exception handlers (e.g. `IMediatorExceptionHandler<TException>`, matched by type, falling back to today's `AddError(e.Message)` as the default) and let them produce the translated message/notification.

   Because this only runs **once**, at the actual `Dispatch`/`Execute` call the application code invoked — never once per nesting level — it structurally cannot produce the cascade in this report: there is no "inner middleware translates and swallows, outer middleware sees a wrapped `MediatorExecutionException` and treats it as unexpected" sequence, because there is only ever one place doing the catching, and it is the library's own code, not N stacked copies of an app-supplied middleware. `ErrorHandlingMiddleware`-style per-project logic (typed `catch` branches → translated message → optional email alert) would become a set of small, individually registered exception handler services instead of one large middleware — same behavior, but centralized where the library controls the invocation count.

Option 3 requires no public API break (it can be adopted per-middleware, opt-in, by consumers, or the library can define the convention/marker). Option 4 is a more invasive but arguably cleaner redesign: it moves the "which exceptions are expected vs. unexpected" decision out of a general-purpose middleware slot entirely and into a first-class, typed extension point on the mediator itself.
