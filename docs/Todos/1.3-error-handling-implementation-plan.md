## Purpose of this document

1.2 describes *what* to build and *why*, at the level of a design decision. This document breaks that design into small, independently shippable, independently testable units of work — each with its own acceptance criteria and a concrete list of test cases — so implementation can proceed step by step and each step can be verified in isolation before the next one starts.

Each unit below is scoped so that:
- it compiles and passes the full existing test suite on its own (no unit depends on a *later* unit to be correct),
- it ships with the tests that prove it, in the same change,
- it can be reviewed and merged independently of the units that follow it.

Units are ordered by dependency, not by 1.2's section numbers — several 1.2 subsections map to a single unit here, and a couple of 1.2's steps are split further than 1.2's own "Implementation order" (section 5) suggests, specifically so each PR-sized chunk has a clean, testable boundary.

### Already done — out of scope for this plan

1.2 §4 ("Known issues & deferred items") lists two items that read as open work in that document but have already shipped since it was written:

- `MediatorContext.Depth` / `IsNested` — released in 8.4.0.
- HTTP status code hint (`MediatorContextExtensions.SetResponseStatusCodeHint`) — released in 8.5.0.

Neither needs any work here. They're mentioned only so nobody re-derives them while implementing Unit 3 (`ExecuteUnhandled` re-throw bridge), which does read `context.IsNested`/`ParentContexts`.

### Current baseline (verified against source, 2026-07-31)

- `Pipaslot.Mediator/Mediator.cs`: `Dispatch` (19-42) and `Execute<TResult>` (65-97) each wrap `ProcessPipeline` in `try/catch (Exception e) { context.AddError(e.Message); return ...; }`. `DispatchUnhandled` (44-63) and `ExecuteUnhandled<TResult>` (99-135) have no catch at all.
- `Pipaslot.Mediator/MediatorExecutionException.cs`: single class, three static factories (`CreateForUnhandledError`, `CreateForNoHandler`, `CreateForMissingResult`), no subtypes.
- `Pipaslot.Mediator/Middlewares/MediatorContext.cs`: single `_results` list holding both handler results and `Notification`s; no `Exceptions` collection exists yet. `AddError` lives as an extension method in `MediatorContextExtensions.cs` (48-65), not on the context itself.
- `Pipaslot.Mediator/Middlewares/Handlers/HandlerExecutor.cs` + `MessageHandlerExecutor<TMessage>` / `RequestHandlerExecutor<TRequest,TResult>`: the abstract-base + closed-generic-per-type-executor pattern that Unit 2 mirrors for exception handlers.
- `Pipaslot.Mediator/Configuration/ReflectionCache.cs`: two-tier `Dictionary` (startup) + `ConcurrentDictionary` (runtime, lazy) cache — the pattern Unit 2 mirrors for exception-type → handler-entry resolution.
- `Pipaslot.Mediator.Http/MediatorMiddleware.cs`: server only ever calls `Dispatch`/`Execute`, never the `*Unhandled` variants — confirms the "no internal message leaks past `Execute`/`Dispatch`" guarantee (2.6 in 1.2) is the one that actually matters for the HTTP transport.
- Unit 0/1 closed the original "no test exercises `ExecuteUnhandled`/`DispatchUnhandled`" gap — see the coverage map below for what's covered where.

## Unit 0 — Safety net: characterization tests for current behavior

**Goal:** lock down today's observable behavior *before* touching it, so every later unit has a regression baseline and a clear diff of what changed on purpose.

**Why first:** none of `Dispatch`/`Execute`/`DispatchUnhandled`/`ExecuteUnhandled` currently has direct test coverage for the exception paths (per the source survey above — `ExecuteUnhandled`/`DispatchUnhandled` have zero references in `tests/`). Refactoring the catch boundary without this net means any accidental behavior change (e.g. in the `NoHandlerFound`/`MissingResult` ordering) is invisible until a consumer app notices it.

**Scope:**
- New test class(es), root-level alongside `Mediator_CancellationTests.cs`, covering *current* behavior only — no new production code. (Shipped as a single `Mediator_ErrorHandlingTests.cs`; later split during Unit 1 review into `Mediator_NestedUnhandledCollapseTests.cs` and `Mediator_ExecutionExceptionSubtypeTests.cs` per the coverage map above — use those two names going forward.)

**Test cases:**
- `Dispatch`/`Execute`: handler throws → response has `Success == false`, `Results` contains a `Notification` whose `Content == exception.Message` (today's raw-message leak, documented as a test so Unit 4 can flip it on purpose).
- `Dispatch`/`Execute`: no handler registered → response has `Success == false` (current code swallows `CreateForNoHandler` into the same catch, per `Mediator.cs:30-33`+`37-41` — confirm this is genuinely what happens today, since it means the exception's own message becomes the `Notification.Content`).
- `DispatchUnhandled`/`ExecuteUnhandled`: handler throws → the *original* exception propagates unmodified (no wrapping) — confirm today's contract before Unit 3 changes it for the `AddException` case.
- `DispatchUnhandled`/`ExecuteUnhandled`: middleware sets `Status = Failed` without throwing → `MediatorExecutionException.CreateForUnhandledError` is thrown, message contains the notification content.
- `DispatchUnhandled`/`ExecuteUnhandled`: no handler registered → `MediatorExecutionException.CreateForNoHandler` is thrown (not swallowed, unlike the `Dispatch`/`Execute` case above).
- `ExecuteUnhandled`: handler succeeds but returns no result of `TResult` → `MediatorExecutionException.CreateForMissingResult`.
- Nested case reproducing 1.0's mechanism: outer handler calls `mediator.ExecuteUnhandled(actionB)`, inner handler for B sets `Status = Failed` via `context.AddError(...)` (no throw) → confirm the parent ends up with **both** the propagated `Notification` (via `NotificationPropagationMiddleware`) **and** the outer catch sees `CreateForUnhandledError`'s wrapper message once it bubbles past an unguarded outer `Dispatch`/`Execute`. This is the exact regression test for the bug in 1.0 — keep it and re-target its assertions in Unit 3/4 rather than deleting it.

**Acceptance criteria:** all new tests pass against current `main`/`error-handlers` code, unmodified. This unit is pure test-authoring — a reviewer should be able to verify "no production file changed" from the diff alone.

## Unit 1 — `MediatorExecutionException` subtypes + built-in boundary rules

Maps to 1.2 §2.3 + the `MediatorUnhandledErrorException` boundary rule referenced in §2.2's implementation-order note. Deliberately kept separate from Unit 2 (typed exception handlers) — this unit fixes the reported alert-noise bug (1.0) with **zero new public extension points**, so it can ship and be validated against the real FIT.WebApi consumer before the larger Unit 2/3 surface lands.

**Scope:**
- `Pipaslot.Mediator/MediatorUnhandledErrorException.cs`, `MediatorNoHandlerFoundException.cs`, `MediatorMissingResultException.cs` — each `: MediatorExecutionException`, no new members (per 1.2 §2.3's code block).
- `MediatorExecutionException.CreateForUnhandledError` → returns `MediatorUnhandledErrorException`; `CreateForNoHandler` → `MediatorNoHandlerFoundException`; `CreateForMissingResult` → `MediatorMissingResultException`. Change the *return type* of each factory to the specific subtype (source-compatible: callers already type the variable as `MediatorExecutionException` or `var`).
- No behavior change to `Dispatch`/`Execute`/`DispatchUnhandled`/`ExecuteUnhandled` yet — this unit only changes *which type* gets thrown, not *when*.

**Explicitly not in scope for this unit:** the "log Warning not Error for `MediatorUnhandledErrorException`, no default alert" behavior from 1.2 §2.3 has no code home yet at this point (there's no built-in logging middleware that owns this decision) — that lands as part of Unit 4, where the boundary rules actually get enforced at `Execute`/`Dispatch`. This unit only makes the type distinction *possible* for consumers who already catch `MediatorExecutionException` and want to add a type-based branch themselves ahead of the library doing it for them.

**Test cases** (extend `Mediator_ExecutionExceptionSubtypeTests.cs` from Unit 0 rather than duplicating setup):
- Each of the three failure conditions (`Status = Failed` without throw, no handler, missing result) now throws the correct **subtype**, verified via `Assert.IsType<T>` (not just `is MediatorExecutionException`).
- Existing consumer-style `catch (MediatorExecutionException)` still catches all three subtypes (compile-time + runtime check — a test that catches the base type and asserts it ran, for each of the three triggers).
- `Response` property (existing `IMediatorResponse Response { get; }`) is populated identically on the subtype as it was on the base type before this change — no regression in what's readable off a caught exception.

**Acceptance criteria:** Unit 0's tests still pass except the ones asserting the exact runtime type was `MediatorExecutionException` (those get updated in place to assert the specific subtype — call this out explicitly in the PR description since it's an intentional test change, not a dropped assertion).

## Unit 2 — Typed exception handler registration, resolution and invocation

Maps to 1.2 §2.2 in full (§2.2.1 through §2.2.5). This is the largest unit; 1.2 already sequences it internally as one piece of work ("Includes the inheritance resolution, the executor bridge and the cache"), and splitting it further would leave intermediate states where the resolution cache exists but nothing can register into it — not independently testable. Kept as one unit, but the test list below is organized by sub-concern so review can proceed sub-concern by sub-concern.

**Deliberately excluded from this unit:** wiring resolution into `Execute`/`Dispatch` (that's Unit 4 — this unit builds and tests the resolver/executor as a standalone component with its own test host, not yet reachable from the public `IMediator` entry points).

**Scope:**
- `Pipaslot.Mediator/IMediatorExceptionHandler.cs` — `public interface IMediatorExceptionHandler<TException> where TException : Exception`.
- `Pipaslot.Mediator/MediatorAmbiguousExceptionHandlerException.cs` — `: MediatorException`.
- `Configuration/IMediatorConfigurator.cs` / `MediatorConfigurator.cs`: `AddExceptionHandler<THandler>(ServiceLifetime = Transient)`, `AddExceptionHandlers(IEnumerable<Type>, ServiceLifetime = Transient)` — mirrors `AddHandlers`' shape, no assembly-scanning overload (1.2 §2.2.1 explains why: eager duplicate-detection must depend on what's written at the call site, not on assembly contents).
- Startup-time routing collection on `MediatorConfigurator` (mirrors `ReflectionCache`'s `_startupTimeActions` shape): `GetInterfaces()` scan per registered handler type, `(ExceptionType, ExecutorType)` entries via `typeof(ExceptionHandlerExecutor<>).MakeGenericType(exceptionType)`.
- `Middlewares/Handlers/ExceptionHandlerExecutor.cs` (abstract) + closed-generic `ExceptionHandlerExecutor<TException>` — mirrors `HandlerExecutor`/`MessageHandlerExecutor<TMessage>`, resolves `IMediatorExceptionHandler<TException>` via `GetService` (not `GetRequiredService` — must tolerate `null` per 2.2.5), invokes it in its own `try/catch` so a throwing handler degrades to "no match" rather than escaping.
- Resolution cache: `ConcurrentDictionary<Type, ExceptionHandlerEntry?>` keyed by concrete runtime exception type, memoizing both positive and negative (`null`) results. Matching via `IsInstanceOfType`, specificity via `IsAssignableFrom` per 1.2 §2.2.3 (class beats interface on ties; throws `MediatorAmbiguousExceptionHandlerException` on genuine ambiguity).
- Eager duplicate-registration check: registering a second handler for an exception type already registered through the configurator throws at startup (`MediatorException`, not the ambiguous-handler exception — this is a distinct, exact-key case per 2.2.5).
- Freeze the routing collection once the container is built (no runtime add/remove — 2.2.5's closing constraint).

**Test cases** (new test class, e.g. `tests/Pipaslot.Mediator.Tests/Middlewares/ExceptionHandlerResolutionTests.cs`, built against a standalone `ServiceProvider` + the resolver component directly — does not need `IMediator` wired up; this is a genuinely new trigger condition, not covered by the coverage map above, so a new file is correct here — add a row for it once written):

*Registration (2.2.1):*
- `AddExceptionHandler<T>` where `T` implements `IMediatorExceptionHandler<TException>` for one type → one routing entry, correct `ExceptionType`.
- `AddExceptionHandler<T>` where `T` implements the interface for *two* exception types → two routing entries, same backing service type.
- `AddExceptionHandler<T>` where `T` implements no `IMediatorExceptionHandler<>` at all → throws at startup (configuration bug, eager).
- Default lifetime is `Transient`; explicit `ServiceLifetime.Singleton` overrides it and is honored by DI resolution.
- `AddExceptionHandlers(IEnumerable<Type>)` registers all given types with the same validation as the single-type overload.

*Resolution / specificity (2.2.2, 2.2.3):*
- Handler registered for `ValidationException`; thrown type is `ValidationException` exactly → resolves.
- Handler registered for `ValidationException`; thrown type is `FieldValidationException : ValidationException` → resolves to the `ValidationException` handler (subtype fallback).
- Handlers registered for both `ValidationException` and `Exception` (base); thrown type is `FieldValidationException : ValidationException` → resolves to the more specific `ValidationException` handler, not `Exception`.
- Handlers registered for a class (`ValidationException`) and an unrelated interface (`IUserFacingException`) both implemented by the same concrete exception → class wins deterministically (no ambiguity throw).
- Handlers registered for two *unrelated* interfaces both implemented by the same concrete exception → throws `MediatorAmbiguousExceptionHandlerException` naming the concrete type and both candidates.
- Exception type with no matching handler at all → resolution returns "no match" (not a throw) — the negative result the fallback (Unit 4) will use.
- Negative-result caching: resolve an unmapped type twice, assert the routing-entry scan only executes once (e.g. via a call-counting test double or an entry set that would throw on a second scan) — proves the `ConcurrentDictionary<Type, Entry?>` caches `null` too, not just hits.
- Positive-result caching: resolve a mapped type twice, second call does not re-run the `IsInstanceOfType`/`IsAssignableFrom` comparison set (same call-counting approach).

*Invocation / fault isolation (2.2.2's "must be wrapped in try/catch" requirement):*
- Registered handler's `Handle` method throws → resolution/invocation degrades to "no match" outcome, **original** exception is what the caller ultimately observes (not the handler's own exception) — this is the "must never mask the original exception" requirement, and is the single most important test in this unit.
- Handler resolves to `null` via DI (see substitution/removal tests below) at invocation time → same graceful degrade, no `NullReferenceException`.

*Test substitution / removal (2.2.5):*
- `services.AddTransient<IMediatorExceptionHandler<ValidationException>, FakeHandler>()` registered *after* the configurator's own registration → `FakeHandler` is what actually runs (last-registration-wins, standard DI override semantics) — routing entry itself is untouched, only the resolved implementation changes.
- `services.RemoveAll<IMediatorExceptionHandler<ValidationException>>()` after configurator registration → resolution falls back to "no match" (not a throw) at invocation time.
- Registering a **second** handler for `ValidationException` directly through `AddExceptionHandler`/`AddExceptionHandlers` (not via raw DI substitution) → throws at startup (exact-key duplicate, distinct from the ambiguity case above).

**Acceptance criteria:** this unit is fully testable and mergeable with **zero observable change** to `IMediator.Dispatch`/`Execute`/etc. — nothing calls the new resolver yet. A reviewer can verify this by confirming no file under `Mediator.cs` or `MediatorContext.cs` changed in the diff.

## Unit 3 — `context.Exceptions` / `AddException` + `ExecuteUnhandled` re-throw bridge

Maps to 1.2 §2.4. Independent of Unit 2 (does not require typed exception handlers to exist) but depends on Unit 1 (re-throw bridge's "empty `Exceptions`" fallback throws `MediatorUnhandledErrorException`, the Unit-1 subtype).

**Scope:**
- `MediatorContext`: new `private readonly List<Exception> _exceptions` + `public IReadOnlyCollection<Exception> Exceptions => _exceptions;` — separate from `_results`/`Results` by construction (structural guarantee against client leakage, not a filter).
- `MediatorContextExtensions.AddException(this MediatorContext context, Exception ex)`: sets `Status = ExecutionStatus.Failed`, appends to `_exceptions`. Explicitly does **not** create a `Notification` and does **not** touch `HttpContext` (per 1.2 §2.4's code sample comment).
- `DispatchUnhandled`/`ExecuteUnhandled`: when `Status == Failed`, branch on `context.Exceptions.Count`:
  - `1` → re-throw the original type via `ExceptionDispatchInfo.Capture(ex).Throw()`.
  - `> 1` → throw `AggregateException(context.Exceptions)`.
  - `0` (today's only path, legacy `AddError`-only middlewares) → unchanged: throw `MediatorUnhandledErrorException` (Unit 1's subtype; this is the "fallback wrapper — narrowed role, not removed" from 1.2 §2.4).
- No propagation of `Exceptions` to parent contexts anywhere (no change needed to `NotificationPropagationMiddleware`, which only ever looked at `Results`/`Notification` — confirm this with a test rather than assuming it from reading the code, since it's a "prove the absence of a feature" case).
- Precedence rule when a handler throws **and** middleware already called `AddException` earlier in the same pipeline run: the thrown exception is primary for status/re-throw purposes; anything in `Exceptions` is secondary (log-only — logging itself is Unit 4's concern, this unit just needs the precedence to be structurally correct, i.e. the thrown exception's type is what gets re-thrown, not something reconstructed from `Exceptions`).

**Test cases** (most of this belongs in a new file — `context.Exceptions`/`AddException` and the re-throw bridge are a new trigger condition, not a fit for either existing root-level file's narrow scope; some assertions belong in a new `MediatorContextTests.cs` if one doesn't already cover `AddResult`/`AddError` — check before creating a new file. Check the coverage map above first: the legacy-`AddError`-only regression case is the *existing* `NoHandlerWithoutError`/`NoHandlerAndErrorReturned` rows, not a new test):
- `context.AddException(ex)` sets `Status = Failed`, adds to `Exceptions`, does **not** add anything to `Results`.
- `context.AddException(ex)` does not create any `Notification` (assert `Results` has no `Notification` with matching content).
- `ExecuteUnhandled`/`DispatchUnhandled`: single `AddException(new ValidationException(...))` recorded by a middleware (no throw) → caller receives the **original** `ValidationException`, not a wrapper, and its stack trace is preserved where the runtime supports it (`ExceptionDispatchInfo` round-trip).
- `ExecuteUnhandled`/`DispatchUnhandled`: two middlewares each call `AddException` with different exception types → caller receives `AggregateException` containing both, in recording order.
- `ExecuteUnhandled`/`DispatchUnhandled`: `Status = Failed` via legacy `context.AddError(...)` only (no `AddException` call anywhere) → still throws `MediatorUnhandledErrorException` exactly as before Unit 1/3 (regression guard tying back to Unit 0's baseline test).
- Handler throws directly **and** an earlier middleware in the same pipeline called `AddException` with a *different* exception → the directly-thrown exception is what the caller receives (precedence rule), the `AddException`-recorded one is not silently substituted or lost (assert it's still readable off `context.Exceptions` for whichever logging step reads it later).
- Nested case: inner `Execute`/`Dispatch` (not `*Unhandled`) records via `AddException` and fails; outer handler inspects `response.Success` and recovers (doesn't rethrow) → outer/parent context's own `Exceptions` collection is empty (no auto-propagation — the explicit "verified" case from 1.2 §2.4).
- Nested case: inner `ExecuteUnhandled` call's exception (whether re-thrown original, `AggregateException`, or `MediatorUnhandledErrorException` fallback) is treated by the *outer* pipeline exactly like any other directly-thrown exception — no special-casing needed, but worth one test proving the outer catch boundary (Unit 4, forward-reference) doesn't need to know anything about `Exceptions` to handle it correctly.

**Acceptance criteria:** `ExecuteUnhandled`/`DispatchUnhandled` behavior for the *existing* `AddError`-only path is unchanged (Unit 0 baseline still green); new `AddException` path is additive and fully covered before Unit 4 wires typed handlers into the boundary that will eventually populate `Exceptions` from caught exceptions too.

## Unit 4 — Wire it all together at the `Execute`/`Dispatch` boundary (safe-by-default)

Maps to 1.2 §2.1 (entry-point contract table), §2.2 (dispatch actually happening), §2.3's logging rules, and §2.6 (safe-by-default fallback). This is where the four preceding units stop being independently-inert and become the library's actual new behavior — necessarily the riskiest unit, so it's scoped last and kept as small as possible given everything else is already built and tested.

**Scope:**
- `Mediator.Dispatch` / `Mediator.Execute<TResult>`: replace `catch (Exception e) { context.AddError(e.Message); ... }` with:
  1. Resolve a typed handler via Unit 2's executor for the caught exception's runtime type.
  2. Match found → handler produces the client-facing message/notification; log **before** applying the translation (2.6: log always has original detail even when client gets the generic message).
  3. No match (including the exception being a `MediatorUnhandledErrorException` from a nested `*Unhandled` call, or `MediatorNoHandlerFoundException`/`MediatorMissingResultException`) → apply the §2.3 default rules:
     - `MediatorUnhandledErrorException` → do **not** add `e.Message` again (already-translated content is already in `context.Results` from the inner pipeline); `Status = Failed`; log **Warning**; no default alert.
     - `MediatorNoHandlerFoundException` / `MediatorMissingResultException` → generic safe message to `Results`; log **Error** with full detail.
     - Anything else unmapped → generic safe message to `Results`; log **Error** with full detail (this is the behavioral break called out in 1.2 §3 — replaces today's 1:1 `AddError(e.Message)`).
- `context.Exceptions` is never read when building `Results`/serializing to the client, under any code path (test this directly, don't just infer it from Unit 3's structural separation still holding).
- No change to `DispatchUnhandled`/`ExecuteUnhandled` beyond what Unit 3 already did — per the 1.2 §2.1 contract table, they still never catch.

**Test cases** (this is where Unit 0's baseline tests get their final, intentional updates, in whichever file the coverage map says owns each trigger. Check the coverage map above first — the unmapped-exception and `MediatorNoHandlerFoundException`/`MediatorMissingResultException` scenarios below update the existing `BasicFailing`/`Nohandler`/`ResultWasTakenFromTheContext` rows in place rather than adding parallel tests; the nested-call and end-to-end regression scenarios extend `Mediator_NestedUnhandledCollapseTests.cs`):
- Unmapped exception thrown by a handler, reached via `Dispatch`/`Execute` → `Results` contains a **generic** message, not `e.Message` (the security-relevant assertion from 1.2 §2.6 — replaces the Unit 0 baseline test that asserted the raw message leaked).
- Same unmapped-exception scenario → server log (via injected `ILogger`/test sink) contains the **original** exception detail, logged at **Error**.
- Exception type with a registered `IMediatorExceptionHandler<TException>` (Unit 2), thrown by a handler, reached via `Dispatch`/`Execute` → `Results` contains exactly the message the typed handler produced (not the generic fallback).
- Nested-call regression from 1.0/Unit 0: outer `Dispatch`/`Execute` around an inner `ExecuteUnhandled` whose inner pipeline recorded via `AddException` (Unit 3) and re-threw the original type → outer boundary resolves a typed handler (if any) for that **original** type, not for `MediatorUnhandledErrorException` — proves the fix actually addresses 1.0's root cause (previously: outer only ever saw the generic wrapper type).
- Nested-call case where the inner pipeline is *legacy* (`AddError` only, no `AddException`) → outer boundary receives `MediatorUnhandledErrorException`, does not re-add the message to `Results` (no duplication), logs at **Warning**, does not trigger whatever "unexpected" escalation path a consumer might hook into the Error-level log.
