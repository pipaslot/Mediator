# Pipaslot.Mediator — Built-in Error Handling Redesign

Status: Approved for implementation (next major version)
Decision Makers: Petr (library author)
Date: 2026-07-18

---

## ADR Summary

Decision Makers: Petr

Problem:
--------
- Exception handling was left entirely to consumer-authored `ErrorHandlingMiddleware`; the library only did a hardcoded `catch { context.AddError(e.Message) }` in `Dispatch`/`Execute`.
- Consumer error-handling middleware runs **once per pipeline execution**, including nested calls. A nested `ExecuteUnhandled` whose inner pipeline fails "normally" (validation, not-found) gets its failure translated+swallowed by the inner middleware, re-signaled as a generic `MediatorExecutionException` wrapper, then caught by the **outer** middleware instance as an UNEXPECTED error → false-positive Error logs + alert emails + duplicated/technical messages on the UI.
- `MediatorExecutionException` conflates three qualitatively different situations (handled business failure, no handler registered, missing result) with no discriminator other than free-text `Message` → consumers forced into fragile string matching.
- `context.AddError(e.Message)` sends raw exception messages into `Results` consumed by the Blazor WASM client → real risk of leaking internal details (SQL, connection strings, stack fragments) to the front-end.

Decision:
---------
- Exception catching/translation will move out of the middleware concept into the library itself, bound to the **entry-point contract**: `Execute`/`Dispatch` catch and translate; `ExecuteUnhandled`/`DispatchUnhandled` and the middleware pipeline never catch — exceptions propagate raw.
- handling in `Execute`/`Dispatch` will guarantee that no internal mesage (not translated) is exposed out of the server as the ASP.NET MediatorMiddleware uses those method when receiving actions from the HTTP request.
- Translation will be dispatched to DI-registered, typed exception handlers (working name `IMediatorExceptionHandler<TException>`), resolved by exception type at the `Execute`/`Dispatch` boundary only.
- `MediatorExecutionException` will be split into subtypes (all deriving from it for catch-compatibility): `MediatorUnhandledErrorException`, `MediatorNoHandlerFoundException`, `MediatorMissingResultException`.
- A new server-side-only collection `context.Exceptions` + `context.AddException(ex)` will let middlewares record typed failures **without throwing** (no stack-unwinding overhead). Never stored in `Results`, never serialized to the client.
- Default fallback for unmapped exceptions will be safe-by-default: generic user message to `Results`, full detail only to server log. The current 1:1 `AddError(e.Message)` behavior is removed (behavioral breaking change → major version).

Notes:
------
Rejected: enum discriminator on a single exception type (would force branching inside one handler, bypassing the new type-based dispatch). Rejected: whitelisting `MediatorExecutionException` wholesale in consumer middleware (would silently swallow genuine deployment/config bugs). Rejected: auto-propagating the `Exceptions` collection to parent contexts (parent that recovers via nested `Execute` must not inherit already-recovered errors).

Suggested filename: `2026-07-18 Mediator-Builtin-Error-Handling.md`

## 1. Root cause (from issue report)

Full report: [1-issue-nested-execute-unhandled-exception-collapse.md](1-issue-nested-execute-unhandled-exception-collapse.md). Related research: [1.1-analysis-mediatr-error-handling-comparison.md](1.1-analysis-mediatr-error-handling-comparison.md) (MediatR exception-handling comparison and the open questions that informed this decision). Mechanism in short:

1. Nested `ExecuteUnhandled(actionB)`; handler B fails (exception or validation).
2. Inner instance of consumer `ErrorHandlingMiddleware` catches, translates, calls `AddError`, does **not** rethrow.
3. `NotificationPropagationMiddleware` (outermost of the inner pipeline) propagates the translated notification to the parent context — this happens **before** status inspection.
4. `ExecuteUnhandled` sees `Status == Failed` → throws `MediatorExecutionException.CreateForUnhandledError` with a generic wrapper message embedding the already-translated errors.
5. Calling handler doesn't catch → wrapper bubbles into the **outer** pipeline → outer `ErrorHandlingMiddleware` instance treats it as UNEXPECTED (type not whitelisted, and cannot be safely whitelisted because the same type also covers `NoHandler`/`MissingResult` bugs).
6. Result: spurious Error-level log + alert email; `Results` contain both the clean translated message and the technical wrapper text.

Structural cause: N stacked copies of a catch-and-swallow middleware, one per nesting level. The fix removes per-level catching entirely — there is exactly **one** catching boundary, owned by the library.

## 2. Target architecture

### 2.1 Entry-point contract

| Entry point | Catches? | Behavior on failure |
|---|---|---|
| `Execute` / `Dispatch` | **Yes** (library boundary) | Typed handler dispatch → translated message into `Results`, `Status = Failed`, response returned. Never throws. |
| `ExecuteUnhandled` / `DispatchUnhandled` | **No** | Exceptions propagate raw, unmodified, to the caller. Failed status without a thrown exception → see 2.4. |
| Middleware pipeline | **No** | `IMediatorMiddleware` has no catch responsibility. Consumer `ErrorHandlingMiddleware` pattern is deprecated. |

Nested-call guidance (unchanged contract, now enforced by design):
- Caller wants exception-free branching → nested `Execute`/`Dispatch` + check `response.Success`.
- Caller wants failure to propagate as exception to *its own* caller → nested `*Unhandled`. The single exception per failed nested call is the accepted cost of that contract (opt-in per call site).

### 2.2 Typed exception handlers (boundary dispatch)

- `IMediatorExceptionHandler<TException>` registered in DI; boundary resolves by runtime exception type, most-specific first, with **deterministic ordering owned by the library** (own sorted collection — never dependent on DI container enumeration order; MediatR pitfall).
- Registration fits the existing fluent style (`IMiddlewareRegistrator`-like), no parallel convention.
- Fallback for unmapped exception types: generic safe message + full server-side log (see 2.6).

#### 2.2.1 Registration API

Mirrors the existing `AddHandlers` family on `IMediatorConfigurator` (`Configuration/IMediatorConfigurator.cs`) — the handler type is the only parameter, the handled exception types are discovered from its interfaces:

```csharp
IMediatorConfigurator AddExceptionHandler<THandler>(ServiceLifetime lifetime = ServiceLifetime.Transient)
    where THandler : class;
IMediatorConfigurator AddExceptionHandlers(IEnumerable<Type> handlerTypes, ServiceLifetime lifetime = ServiceLifetime.Transient);
```

**No assembly-scanning overload** — deliberate divergence from the `AddHandlers` family, which does offer one. Every exception handler must be named explicitly at the call site, because the set of registered handlers decides which internal detail gets translated into which client-visible message (2.6); that has to be readable from the configuration code alone. Scanning would also make the eager duplicate check (2.2.5) depend on assembly content instead of on what the programmer wrote, and would silently absorb handlers from referenced assemblies. (Resolution itself is order-independent by construction — see 2.2.3 — so this constraint is about visibility and eager validation, not about ranking.)

One registration can cover several exception types — a handler implementing `IMediatorExceptionHandler<ValidationException>` *and* `IMediatorExceptionHandler<TimeoutException>` produces two routing entries pointing at the same service type.

Startup work per registered handler type (same code shape as `ReflectionCache.GetResultType`):

1. Scan `typeof(THandler).GetInterfaces()` for `IMediatorExceptionHandler<>`, take `GetGenericArguments()[0]` as the handled exception type. **No implementation found → throw at startup** (configuration bug, detectable eagerly).
2. Register the **closed** service `IMediatorExceptionHandler<TException>` → `THandler` in `IServiceCollection` under the given lifetime.
3. Append a routing entry `(ExceptionType, ExecutorType)` into the library's own collection, where `ExecutorType = typeof(ExceptionHandlerExecutor<>).MakeGenericType(exceptionType)`.

**Lifetime default = `Transient`**, matching `AddHandlers`. Singleton was considered (handlers are usually stateless translators) and rejected as a *default*: a singleton handler injecting anything scoped (`ICurrentUser`, a `DbContext` used for audit logging) is a captive dependency, and the resulting failure surfaces **inside the error boundary**, where it would mask the original exception — the worst possible place for it. `Transient` can consume scoped services safely and costs one allocation on an already-failed request. Singleton stays available via the parameter for handlers that are genuinely stateless.

#### 2.2.2 Resolution by inheritance — chosen mechanism

Requirement: a handler registered for `ValidationException` must also serve a thrown/recorded `FieldValidationException : ValidationException` — `catch`-block semantics.

Hard constraint: descendants **cannot** be enumerated at startup, because `FieldValidationException` may live in a consumer assembly that is never scanned. Resolution must therefore be lazy (first occurrence of a concrete type) and memoized from then on.

Two concerns are deliberately kept apart here, because conflating them is what makes the design look like it needs dispatch-time reflection:

| Concern | When | Mechanism |
|---|---|---|
| Learning which `TException` a handler serves | Startup, once per handler type | `GetInterfaces()` (2.2.1) |
| Matching a thrown exception to a routing entry | First occurrence of each concrete type | `entry.ExceptionType.IsInstanceOfType(ex)` |
| Invoking the handler in a typed way | Every handled exception | Closed-generic executor, see below |

Decision (2026-07-31):

- **Matching** uses `Type.IsInstanceOfType`, which is the runtime form of `is` — a type-handle check, not metadata reflection. It is *not* worth building a compiled `ex => ex is TException` delegate (`MakeGenericMethod` or `Expression.Compile`): thanks to the memoization below, matching runs once per distinct concrete exception type over the process lifetime, so the difference from an inlined `isinst` is unmeasurable — while `Expression.Compile` would additionally degrade on trimmed/AOT Blazor WASM builds.
- On the first occurrence of a concrete exception type, the boundary tests all routing entries, collects **all** matches, and picks the most specific one (2.2.3).
- The winner is memoized in a `ConcurrentDictionary<Type, ExceptionHandlerEntry?>` keyed by the concrete runtime type. The **negative** result (`null` → 2.6 fallback) must be cached as well, otherwise unmapped exception types re-scan on every occurrence. Mirror the two-tier startup/runtime caching in `Configuration/ReflectionCache.cs`.
- **Invocation** avoids reflection through the executor bridge the library already uses for action handlers: an abstract non-generic `ExceptionHandlerExecutor` with a closed-generic `ExceptionHandlerExecutor<TException>` subclass, created once via `MakeGenericType` at registration time and resolving `IMediatorExceptionHandler<TException>` as a closed service from DI. See `Middlewares/Handlers/HandlerExecutor.cs` — *"Abstraction for generic handler executors to avoid reflection"* — and `MessageHandlerExecutor<TMessage>` for the shape to copy.

Net effect: **all reflection is confined to startup.** The dispatch path is a dictionary lookup plus a virtual call.

Handler resolution *and* invocation must themselves be wrapped in `try/catch`. A handler that throws (or a scope that is already broken) must degrade to the 2.6 fallback and be logged as a secondary failure — it must never replace or mask the original exception.

#### 2.2.3 Specificity and ambiguity

Candidates are ordered by a partial order over their declared exception type: **A is more specific than B when `B.IsAssignableFrom(A)`**. Resolved in this order:

1. Unique most-specific candidate wins — `FieldValidationException` matching both `ValidationException` and `Exception` resolves to `ValidationException`.
2. When two candidates are incomparable, a **class registration beats an interface registration**. Keeps the realistic `ValidationException` vs. `IUserFacingException` marker combination deterministic instead of failing.
3. Still incomparable (two unrelated interfaces implemented by the same exception) → throw `MediatorAmbiguousExceptionHandlerException : MediatorException` naming the concrete type and both candidates. This is a configuration bug; the boundary treats it as unexpected (Error log + generic client message, per 2.6).

Ambiguity cannot be detected at startup for the same reason descendants cannot — it surfaces on the first occurrence of the offending concrete type. Registering handlers only on classes is ambiguity-free by construction (the `BaseType` chain is linear); interfaces are what introduce case 3.

Scope of the "deterministic ordering owned by the library" requirement: it governs **which exception type routes where** (the rules above, evaluated over the library's own collection). It deliberately does *not* govern which implementation instance serves an already-resolved closed `IMediatorExceptionHandler<TException>` — that is plain DI resolution, and 2.2.5 depends on it.

#### 2.2.4 Cost profile

| Path | Work |
|---|---|
| Steady state (every exception) | one `ConcurrentDictionary<Type, _>` lookup + virtual call into the executor |
| First occurrence of a concrete type | N × `IsInstanceOfType` + `IsAssignableFrom` comparisons across the matched candidates only |
| Startup | `GetInterfaces()` + `MakeGenericType` per registered handler |

#### 2.2.5 Replacing and removing handlers (testability)

Routing (2.2.2) is keyed by exception type, while the implementation comes from DI. That split means standard `Microsoft.Extensions.DependencyInjection` overrides work without any bespoke API:

```csharp
// substitute in a test
services.AddTransient<IMediatorExceptionHandler<ValidationException>, FakeValidationExceptionHandler>();
// remove entirely -> boundary falls back to 2.6
services.RemoveAll<IMediatorExceptionHandler<ValidationException>>();
```

- The executor resolves via `GetService<IMediatorExceptionHandler<TException>>()`, so **the last registration wins** — MEDI's own override convention, which is what makes the substitution above work.
- The executor must tolerate a routing entry whose DI service was removed (resolves to `null`) and degrade to the 2.6 fallback rather than throwing.
- Registering a **second handler for an exception type already registered through the configurator** throws at startup. Exact-key duplicates *are* detectable eagerly (unlike 2.2.3 ambiguity), so this stays fail-fast; test substitution goes through the DI layer above, not through a repeated `AddExceptionHandler`.
- The routing collection is **frozen once the container is built**. No runtime add/remove: the memoization cache in 2.2.2 has no invalidation logic, and immutability is what makes it correct.

### 2.3 `MediatorExecutionException` subtypes

```csharp
public class MediatorUnhandledErrorException : MediatorExecutionException { }  // CreateForUnhandledError
public class MediatorNoHandlerFoundException : MediatorExecutionException { } // CreateForNoHandler
public class MediatorMissingResultException  : MediatorExecutionException { } // CreateForMissingResult
```

- Existing consumer `catch (MediatorExecutionException)` blocks keep working (backward compatible).
- Built-in boundary rules:
  - `MediatorUnhandledErrorException` → errors were already translated and propagated by the inner pipeline; **do not add `e.Message`**; `Status = Failed`; log **Warning** with full context (action, parent action, errors); **no default alert/escalation**. Rationale: the library cannot distinguish "expected user-input validation failure" from "broken inter-module contract (changed validation rules)" — only the consumer can; escalation to Error/alert is consumer opt-in (per type or per action).
  - `MediatorNoHandlerFoundException` / `MediatorMissingResultException` → genuine config/code bugs; default = unexpected: safe message to client, Error-level log with full detail.

### 2.4 `context.AddException` — recorded (non-thrown) failures

- New server-side collection `context.Exceptions` (separate from `Results` — structural guarantee against client leakage; filtering `Results` by type was rejected as a blacklist approach).
- Middlewares record typed failures without throwing:

```csharp
// Validation middleware, target state:
var validationErrors = await _validationProvider.Validate(context.Action);
if (validationErrors.Any())
{
    context.Status = ExecutionStatus.Failed;
    context.AddException(new ValidationException(validationErrors)); // typed, server-side only
    // NO Notification created here. NO HttpContext access here (see TODO doc).
    return; // short-circuit, next() not called
}
```

- User-facing message is produced **exclusively** at the root boundary by translating the recorded/thrown exception. One translation point, one message.
- `ExecuteUnhandled` bridge for recorded exceptions: `Status == Failed` + non-empty `Exceptions` →
  - exactly one recorded exception → re-throw the **original type** via `ExceptionDispatchInfo.Capture(ex).Throw()` (preserves stack trace where one exists);
  - multiple recorded exceptions → throw `AggregateException` (non-standard state caused by consumer branching; handling it is the consumer's responsibility);
  - `Failed` with **empty** `Exceptions` (legacy `AddError`-only middlewares) → throw `MediatorUnhandledErrorException` (fallback wrapper — narrowed role, not removed).
- No automatic propagation of `Exceptions` to parent contexts. Verified:
  - nested `Execute`: parent reacts to failed response; recovered errors die with the inner context (desired);
  - nested `ExecuteUnhandled`: the exception itself travels to the parent — same handling as if thrown directly.
- Precedence when both occur (handler throws AND context has recorded exceptions): thrown exception is primary for status/re-throw; recorded ones go to the log.

### 2.5 Notification asymmetry (transition only)

Problem: with legacy middlewares, the translated `Notification` is propagated to the parent **before** `*Unhandled` throws; a parent that catches and recovers leaves a stale error notification in the UI.

- Target state: no notification is created at the failure site at all (2.4) → asymmetry disappears structurally.
- Transitional workaround for consumers staying on `Notification` + `Failed`: set `StopPropagation = true` on notifications not intended as direct user messages. Recorded as **known issue / migration step**, not a permanent convention (avoids a silent, forgettable convention — MediatR pitfall class).
- Non-breaking: `AddException` is additive; `StopPropagation` exists today.

### 2.6 Safe-by-default client output (security)

- Remove `context.AddError(e.Message)` 1:1 for unmapped exceptions. Default: generic message to `Results`, full exception to server log only. `Results` are consumed by the Blazor WASM client — treat every string in them as public.
- `context.Exceptions` is never serialized to the client under any configuration.
- Log **before** applying the consumer's translation rule, so the log always contains the original detail even when the client receives a generic message.

## 3. Compatibility & migration (15 consuming applications)

| Change | Breaking? | Notes |
|---|---|---|
| Subtypes of `MediatorExecutionException` | No | Derive from existing type; existing catches work. |
| `AddException` / `context.Exceptions` | No | Additive API. |
| `AddExceptionHandler*` family + `MediatorAmbiguousExceptionHandlerException` | No | Additive API; new exception type derives from `MediatorException`. |
| `StopPropagation` workaround | No | Existing API. |
| Removal of 1:1 `AddError(e.Message)` default | **Yes (behavioral)** | User-visible messages change; requires major version + migration guide. |
| Deprecation of consumer `ErrorHandlingMiddleware` pattern | **Yes (conceptual)** | Typed `catch` branches → individual `IMediatorExceptionHandler<T>` registrations; alert/email logic moves there. |

Migration strategy:
- Both worlds coexist during transition: legacy `Notification + Failed` path (fallback wrapper + notification propagation) stays functional for the whole major version; deprecation/removal earliest in the next major.
- Migration guide must cover: (a) porting `ErrorHandlingMiddleware` catch branches to typed handlers; (b) validation middlewares → `AddException`; (c) audit for root-level `*Unhandled` usage (no translation happens there by contract — raw exceptions reach ASP.NET); (d) consumers deciding escalation policy for `MediatorUnhandledErrorException` (default Warning, opt-in alert).

## 4. Known issues & deferred items

1. **Notification asymmetry during transition** — consumer-side `StopPropagation = true` workaround until migrated to `AddException` (2.5).
2. **`IsNested` / `Depth` on `MediatorContext`** — future API improvement; see [2-todo-feature-requests.md](2-todo-feature-requests.md).
3. **HTTP status code hint on context** — separate topic / feature request; key constraint: when the parent recovers the error, the status code must not propagate at all; see [2-todo-feature-requests.md](2-todo-feature-requests.md).
4. **Root-level `ExecuteUnhandled` audit** — consistent with contract, but worth checking across the 15 apps that nobody relies on translation there.

## 5. Implementation order (suggested)

1. Subtypes + built-in boundary rules (fixes the reported issue's alert noise with zero consumer change).
2. Typed exception handler dispatch at `Execute`/`Dispatch` boundary + safe-by-default fallback (closes the WASM leak). Includes the inheritance resolution, the executor bridge and the cache (2.2.2) — cover with tests for: subtype falling back to a base-type handler, most-specific-first when both are registered, negative-result caching, the ambiguity throw, a handler that itself throws (must not mask the original exception), and DI substitution/removal per 2.2.5.
3. `context.Exceptions` + `AddException` + `ExecuteUnhandled` re-throw bridge (`ExceptionDispatchInfo`, `AggregateException` rule).
4. Deprecation annotations + migration guide.
