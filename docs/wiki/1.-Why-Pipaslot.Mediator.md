The Mediator concept is an alternative to SOA (Service-Oriented Architecture), but this library goes one step further by providing abstraction via HTTP for applications using backend for a frontend pattern. It is best suited for .NET Blazor WASM applications.

## When to use it
- You want a single, consistent entry point for all business actions instead of scattering calls across many services and interfaces.
- You need consistent validation, error handling, and other cross-cutting behavior applied uniformly around operations, without decorator chains.
- You want the same [request](2.-Core-concepts-and-glossary.md#request)/[handler](2.-Core-concepts-and-glossary.md#handler) to run in-process and also be exposable over HTTP with authorization, without writing two implementations.
- You need clear, composable flow control between success, validation, and error outcomes.
- You want to decouple the caller from the code that executes the action.

## When not to use it
- Raw throughput is critical and the pipeline/dispatch indirection is not acceptable overhead.
- You need a straightforward, directly navigable call stack (jumping through a mediator makes "who calls what" harder to trace in an IDE).
- You prefer a service class per domain area with a name describing everything it does. A single class can implement multiple [handler](2.-Core-concepts-and-glossary.md#handler) interfaces, but then its name no longer matches every action it handles.

See [Mediator vs SOA](#mediator-vs-soa) below for the trade-offs behind these guidelines.

## Mediator vs SOA
Mediator vs SOA (Service-Oriented Architecture) is usually the first design decision when structuring an application's internal layer. SOA groups domain functionality into cohesive services (e.g. `OrderService`, `UserService`) that callers invoke directly. Mediator instead encapsulates each use case as an [action](2.-Core-concepts-and-glossary.md#action) dispatched through a [pipeline](2.-Core-concepts-and-glossary.md#pipeline) to a single handler.

| | SOA | Mediator |
|---|---|---|
| Organization | By domain/service | By use case/action |
| Coupling | Callers depend directly on service contracts | Callers depend only on the action, not on who executes it |
| Cross-cutting concerns (validation, auth, logging) | Often duplicated across services | Centralized once in [middleware](6.-Pipelines-and-Middlewares.md) |
| Command/query separation | Often blurred into CRUD-like services | Explicit, via separate [Message](2.-Core-concepts-and-glossary.md#message) vs [Request](2.-Core-concepts-and-glossary.md#request) pipelines |
| Navigability / debugging | Straightforward call stack | Extra indirection through the mediator and pipeline |
| Reuse | Operations composed by calling other services directly | Handlers are typically use-case specific and compose less naturally |

Neither approach replaces the other everywhere - many applications keep SOA-style services at the boundary between subsystems, and use Mediator to orchestrate use cases within a subsystem.

## Decouple services and structure your application
Replace direct service-to-service calls with actions and handlers, so each use case is isolated, independently testable, and easy to reason about. Cross-cutting concerns (validation, authorization, transaction scope, caching, error handling) are centralized in middleware instead of duplicated per handler, and CQRS-style separation between Messages (state-changing) and Requests (read-only) lets each get its own middleware stack for dedicated pre/post-processing and telemetry. Handlers and middlewares can also invoke other actions for controlled orchestration, execution is asynchronous with flexible awaiting, and every response carries a full result envelope (e.g. validation summaries, notifications, domain events) back to the caller.<br>
See [Mediator API](5.-Mediator-API.md) and [Pipelines and Middlewares](6.-Pipelines-and-Middlewares.md).

## Unify client-server communication
Use mediator actions as a lightweight, strongly typed protocol between client and server (e.g. Blazor WASM) instead of manually defining and maintaining a REST or gRPC API. Actions and responses are serialized over HTTP with compile-time type safety and predictable contracts, common DTOs/message contracts are shared between client and server, and both sides expose the same `IMediator.Execute()`/`Dispatch()` programming model.<br>
See [Quickstart: Client-Server (Blazor WASM) usage](4.-Quickstart-Client-Server-Blazor-WASM-usage.md) and [HTTP transport and configuration for Client-Server usage](8.-HTTP-transport-and-configuration-for-Client-Server-usage.md).

## Centralize access control
Mediator's single entry point for executing business actions makes it ideal for consistent, centralized authorization instead of scattering `[Authorize]` attributes or role checks across controllers or services. Authorization can be applied globally (via middleware), per-action (via metadata like `[RolePolicy("Admin")]`), or context-aware (fine-grained checks in the handler itself) - and stays unified across client and server tiers when actions carry authorization context (e.g. JWT, identity claims) over HTTP.<br>
See [Authorization](7.-Authorization.md).

## Library structure
For reference, here is how the capabilities described above are split across two NuGet packages (since version 4):
**Pipaslot.Mediator** 
- Core logic and interfaces defining mediator as service, actions, handlers, middlewares 
- `IServiceCollection` extension `.AddMediator()` providing registration for actions, handlers and middlewares

**Pipaslot.Mediator.Http**
- Services with logic for serialization and transferring via HTTP 
- Provide mediator overload `.AddMediatorClient()` which sends actions to the server endpoint by default instead of searching for handlers to execute locally
- Provide mediator overload `.AddMediatorServer()` which converts HTTP content back to mediator action executes Server-side mediator and executes handlers
- `IApplicationBuilder` extension `.UseMediator() registering mediator as middleware for ASP.NET Core request pipeline
