This chapter describes what happens when an [action](2.-Core-concepts-and-glossary.md#action) fails: which entry point throws and which one does not, what the caller and the client actually see, and how to translate your own business exceptions into messages you are willing to show a user.

It starts with the reasoning behind the two entry-point families (Explanation), then documents the API surface (Reference), and closes with step-by-step recipes and migration guidance (How-to).

## Why there are two entry-point families

[Mediator](2.-Core-concepts-and-glossary.md#mediator) exposes each operation twice: `Dispatch`/`Execute` and `DispatchUnhandled`/`ExecuteUnhandled` (see [Mediator API](5.-Mediator-API.md#executeunhandled-and-dispatchunhandled)). The split exists so that each family can offer an unconditional contract instead of a conditional one:

- **The handled family (`Dispatch`, `Execute`) never throws.** Whatever goes wrong - a [handler](2.-Core-concepts-and-glossary.md#handler) throwing, a [middleware](2.-Core-concepts-and-glossary.md#middleware) short-circuiting, a missing handler registration, a cancelled operation - the caller gets a [Response](2.-Core-concepts-and-glossary.md#response) with `Success = false` and an error message. Calling code never needs a `try/catch` around the [mediator](2.-Core-concepts-and-glossary.md#mediator), and that is true unconditionally, not "usually". This is also the only family the HTTP transport uses, so the same guarantee holds in-process and over the network.
- **The unhandled family (`DispatchUnhandled`, `ExecuteUnhandled`) always throws on failure.** It rethrows the original exception with its original type, so the caller can branch on the exception type, inspect its properties, or let it propagate into an outer `try/catch` (including `OperationCanceledException` from a cancelled operation). Use it when you deliberately want failures to interrupt the flow. This holds in the process where the exception was thrown - called on the HTTP client, these methods always throw `MediatorUnhandledErrorException`, because a server-side exception crosses the network as a failed Response and there is nothing left to rethrow (see [In-process exceptions](5.-Mediator-API.md#in-process-exceptions)).

Message translation only ever happens in the handled family. The unhandled family exists precisely to hand you the untranslated exception, so applying a translation there would defeat its purpose.

### Safe by default

An exception that no registered handler translated is **never** reported to the caller verbatim. `Dispatch`/`Execute` put a fixed generic message into the [Result collection](2.-Core-concepts-and-glossary.md#result-collection) and write the full exception - message, stack trace, inner exceptions - to `ILogger` instead.

The reason is that the same `Response` object is serialized and sent to a browser in [Client-Server usage](8.-HTTP-transport-and-configuration-for-Client-Server-usage.md). An `Exception.Message` routinely contains connection strings, file paths, SQL fragments, or entity identifiers, and a rule of "the message reaches the client only when it happens to be harmless" is not a rule anybody can verify. So the library inverts the default: nothing reaches the client until you explicitly say it may, by registering a handler for that exception type.

### What the boundary does with each exception

This is the complete decision table applied by `Dispatch`/`Execute` once an exception reaches them:

| Situation | Message in `Results` | Log |
|---|---|---|
| A registered `IMediatorExceptionHandler<TException>` called `context.SetHandled(message)` | that message | the exception, at the handler's `context.LogLevel` (Warning by default) |
| ...called `context.SetHandledWithoutMessage()` | none - not even an empty-content notification | as above |
| ...returned without calling `SetHandled`/`SetHandledWithoutMessage`, or called `context.SetNotHandled()` | generic message | the exception, at Error |
| ...itself threw | generic message | the **original** exception at Error, plus a separate Error entry for the handler's own exception |
| No handler registered for the exception type | generic message | the exception, at Error |
| `MediatorUnhandledErrorException` (from a nested `*Unhandled` call whose pipeline only used `AddError`) | none added - the nested pipeline's own error messages were already forwarded into this context | Warning |
| `MediatorNoHandlerFoundException`, `MediatorMissingResultException` | generic message | Error |

The log entry always carries the original exception object, including for the translated case - translation changes what the *client* sees, never what the *log* sees, except when the handler explicitly asks for `LogLevel.None` (see [`IMediatorExceptionContext`](#imediatorexceptioncontext) below), which is the one way to opt out.

The Warning/Error split is the escalation signal: `Error` means a bug in the application (a missing registration, an untranslated exception type, a broken handler), while `Warning` means a failure the application already accounted for. A handler can override its own entry's level via `context.SetLogLevel(...)` - to escalate a translated failure that still deserves attention, or to suppress the entry entirely for a handler that already logs the failure itself. If you alert on `Error`-level entries from the mediator, a translated business failure will not page anybody by default.

## Reference

### `IMediatorExceptionHandler<TException>`

```csharp
public interface IMediatorExceptionHandler<in TException> where TException : Exception
{
    Task Handle(TException exception, IMediatorExceptionContext context);
}
```

A handler reports its decision by calling methods on `context` rather than by returning a value - see [`IMediatorExceptionContext`](#imediatorexceptioncontext) below. One class may implement the interface several times to cover several exception types.

Handlers are resolved from DI per invocation, so they can inject services (a localizer, `ILogger`, options, ...). Their `ServiceLifetime` is `Transient` by default and configurable at registration.

### `IMediatorExceptionContext`

`context` is what a handler acts on: besides `Exception`, `Context` (the failing action's [Context](2.-Core-concepts-and-glossary.md#context)) and `CancellationToken`, it groups every decision a handler is allowed to make into four calls - report a client message (`SetHandled(message)`), report none (`SetHandledWithoutMessage()`), reverse an earlier one of those two (`SetNotHandled()`), and override the boundary's own log level for this failure (`SetLogLevel(level)`). What each one does to `Results` and to the log is exactly the table above; `IsHandled`/`Message`/`LogLevel` are the read-only counterparts a test asserts against.

The boundary always passes a `MediatorExceptionContext` - the interface's only concrete implementation - as `context`. Its small surface is deliberate: mock or fake `IMediatorExceptionContext` to unit-test a handler without a DI container or a real `MediatorContext`; see [Unit-test an exception handler](#unit-test-an-exception-handler) below.

### Registration

`AddExceptionHandler<THandler>` and `AddExceptionHandlers(IEnumerable<Type>)` are available on `IMediatorConfigurator`:

```csharp
services.AddMediator()
    .AddExceptionHandler<ValidationExceptionHandler>()
    .AddExceptionHandler<ConcurrencyExceptionHandler>(ServiceLifetime.Singleton)
    .AddExceptionHandlers(new[] { typeof(DomainExceptionHandler), typeof(PaymentExceptionHandler) });
```

The exception types a handler covers are discovered from its `IMediatorExceptionHandler<>` implementations - one routing entry per implemented interface. There is deliberately no assembly-scanning overload: exception routing must be readable from the composition root, not implied by what happens to be in an assembly.

Both methods validate eagerly, at startup:

| Situation | Result |
|---|---|
| The type implements no `IMediatorExceptionHandler<>` | `MediatorException` |
| A handler is already registered for the same exception type | `MediatorException` |

### Resolution rules

When an exception reaches the boundary, the concrete runtime type of the exception is matched against the registered entries:

1. Every registration whose exception type is assignable from the thrown type is a candidate, so a handler registered for a base type also serves its subtypes.
2. The most specific candidate wins - a handler for `ValidationException` beats a handler for `Exception` when a `FieldValidationException` is thrown. `IMediatorExceptionHandler<TException>` constrains `TException` to `Exception`, so every candidate matching the same thrown type necessarily lies on that type's single linear base-class chain, meaning the most specific one is always uniquely determined.
3. The most specific candidate is asked once. If it declines (returns without calling `SetHandled`/`SetHandledWithoutMessage`, or calls `SetNotHandled()`), resolution does **not** retry a less specific match - the exception is treated as unmapped and gets the generic-message/Error-log treatment from the table above.
4. If nothing matches in the first place, the exception is unmapped the same way.

Resolution is memoized per concrete exception type - including "no match" results - so the scan runs once per distinct exception type for the lifetime of the process.

### Fault isolation

A registered handler must never make a failure worse, so the boundary degrades instead of propagating:

- The handler's `Handle` throws → treated as if no handler matched (generic message, Error log with the **original** exception), plus a second, separate Error log entry carrying the handler's own exception - so "the handler is broken" stays distinguishable from "no handler is registered" from the log alone. Mutations the handler already made to `context.Context.Results` before throwing are not rolled back; only the context's own `IsHandled`/`Message` state is discarded.
- The handler cannot be resolved from DI (e.g. removed with `RemoveAll` in a test) → same graceful degrade, no `NullReferenceException`, and no extra log entry - this is not a fault of a handler that ran.

### Exception types thrown by the mediator

| Type | Thrown when |
|---|---|
| `MediatorException` | Configuration error, detected at startup or during pipeline setup. |
| `MediatorExecutionException` | Base type for all execution failures below; exposes the `Response` gathered so far. |
| `MediatorUnhandledErrorException` | `*Unhandled` call whose pipeline failed without recording an exception (status set via `AddError`). |
| `MediatorNoHandlerFoundException` | No handler is registered for the executed action. |
| `MediatorMissingResultException` | The pipeline succeeded but produced no result of the requested type. |

The three specific execution exceptions all derive from `MediatorExecutionException`, so existing `catch (MediatorExecutionException)` blocks keep catching them, and you can add a type-based branch when you want to react differently to "no handler registered" than to "the pipeline reported a failure".

### `context.AddException` and `context.Exceptions`

A [middleware](2.-Core-concepts-and-glossary.md#middleware) that decides an action must fail has two options on the [Context](2.-Core-concepts-and-glossary.md#context):

| Call | Effect |
|---|---|
| `context.AddError(message)` | Sets `Status = Failed` and adds a client-facing error message to `Results`. |
| `context.AddException(exception)` | Sets `Status = Failed` and records the exception in `context.Exceptions`. Adds nothing to `Results`. |

`context.Exceptions` is a separate collection from `Results` by construction, not a filtered view of it, and nothing on the `Dispatch`/`Execute` path ever reads it when building the response. A recorded exception therefore cannot leak to a client, and it is not propagated to parent contexts on nested calls (unlike error notifications, which are - see [Notification propagation across nested calls](9.4.-Cookbook-and-integrations.md#notification-propagation-across-nested-calls)).

What it is for is the `*Unhandled` re-throw bridge:

| Recorded exceptions when a `*Unhandled` call finds `Status = Failed` | Thrown to the caller |
|---|---|
| exactly one | that exception, with its original type and stack trace preserved |
| more than one | `AggregateException` containing them in recording order |
| none | `MediatorUnhandledErrorException` carrying the error messages from `Results` |

If a handler throws directly, that exception wins - it propagates as-is, and anything previously recorded via `AddException` stays readable on `context.Exceptions` for logging purposes.

## How-to

### Translate a business exception into a client-facing message

```csharp
public class ValidationExceptionHandler(IStringLocalizer<Resources> localizer)
    : IMediatorExceptionHandler<ValidationException>
{
    public Task Handle(ValidationException exception, IMediatorExceptionContext context)
    {
        context.SetHandled(localizer["Validation failed: {0}", exception.PropertyName].Value);
        return Task.CompletedTask;
    }
}
```

```csharp
services.AddMediator()
    .AddExceptionHandler<ValidationExceptionHandler>()
    ...
```

Every `ValidationException` (and every subtype of it) thrown by any handler or middleware now surfaces to `Dispatch`/`Execute` callers as that message, and is logged at Warning instead of Error.

### Cover a whole exception family with one handler

Register the handler for the common base type or a marker interface implemented by your exceptions:

```csharp
public interface IUserFacingException
{
    string UserMessage { get; }
}

public class UserFacingExceptionHandler : IMediatorExceptionHandler<Exception>
{
    public Task Handle(Exception exception, IMediatorExceptionContext context)
    {
        context.SetHandled(exception is IUserFacingException e
            ? e.UserMessage
            : "The operation could not be completed.");
        return Task.CompletedTask;
    }
}
```

A handler registered for `Exception` matches everything, which also means it takes over the generic fallback for genuinely unexpected exceptions - including `MediatorNoHandlerFoundException` and `MediatorMissingResultException`, which would otherwise be logged at Error. Prefer registering the narrowest type that covers your family; keep a catch-all only if you are certain you want application bugs reported as Warnings.

### Fail an action without showing the user a message

Some failures should fail the action without putting anything client-facing in `Results` at all - for example when the UI already knows what went wrong from context and a generic notification would just be noise. Call `SetHandledWithoutMessage()` instead of `SetHandled(message)`:

```csharp
public class AlreadyReportedExceptionHandler : IMediatorExceptionHandler<AlreadyReportedException>
{
    public Task Handle(AlreadyReportedException exception, IMediatorExceptionContext context)
    {
        context.SetHandledWithoutMessage();
        return Task.CompletedTask;
    }
}
```

`Response.Success` is still `false` and the exception is still logged at the handler's `LogLevel` (Warning by default) - only the client-facing message is optional, not the failure itself. Call `context.Context.AddError(...)` first if you want your own message instead of none; the boundary never adds a second, generic one on top.

### Decline for some instances of an exception type

A handler registered for a base exception type can inspect the concrete instance and only translate the cases it recognizes - the realistic case being a handler for a shared base type (e.g. a `SqlException`-style hierarchy keyed by error code) that only handles specific subtypes or property values. Returning without calling `SetHandled`/`SetHandledWithoutMessage` declines for that instance, and the exception gets the same generic-message/Error-log treatment as if no handler had matched at all:

```csharp
public class SqlExceptionHandler : IMediatorExceptionHandler<SqlException>
{
    public Task Handle(SqlException exception, IMediatorExceptionContext context)
    {
        if (exception.Number == 2601) // unique constraint violation
        {
            context.SetHandled("This record already exists.");
        }

        // Any other SQL error code: declines, falls back to the generic message and an Error log entry.
        return Task.CompletedTask;
    }
}
```

Resolution asks the single most specific registered handler once - declining does not fall back to search for a less specific match. `SetNotHandled()` is the explicit form of the same thing, useful when a base-class handler's `Handle` already called `SetHandled`/`SetHandledWithoutMessage` and an overriding subclass needs to reverse that decision after inspecting the instance further.

### Fail an action from a middleware while keeping the original exception

```csharp
public class TranslateStorageFailureMiddleware : IMediatorMiddleware
{
    public async Task Invoke(MediatorContext context, MiddlewareDelegate next)
    {
        try
        {
            await next(context);
        }
        catch (StorageException e)
        {
            // Status = Failed, but the exception stays server-side: Dispatch/Execute callers get the
            // generic message, ExecuteUnhandled/DispatchUnhandled callers get this exact exception back.
            context.AddException(e);
        }
    }
}
```

### Report cancellation as something other than a generic failure

A cancelled operation reaches `Dispatch`/`Execute` like any other exception, so by default it produces the generic message and an Error-level log entry. The library ships `OperationCanceledExceptionHandler` for applications where a cancelled action is expected rather than a bug - it is opt-in, because that judgement depends on the application:

```csharp
services.AddMediator()
    .AddExceptionHandler<OperationCanceledExceptionHandler>()
    ...
```

Cancellation then produces `OperationCanceledExceptionHandler.Message` ("The operation was cancelled.") and a Warning-level log entry. `TaskCanceledException` derives from `OperationCanceledException`, so this one registration covers both. To localize the message, derive from the class and override the `GetMessage` extension point instead of `Handle` itself, then register your subclass instead:

```csharp
public class LocalizedCancellationHandler(IStringLocalizer<Resources> localizer) : OperationCanceledExceptionHandler
{
    protected override string GetMessage(OperationCanceledException exception)
        => localizer["The operation was cancelled."].Value;
}
```

Callers of `ExecuteUnhandled`/`DispatchUnhandled` keep receiving the original `OperationCanceledException`/`TaskCanceledException` regardless of this registration.

### Unit-test an exception handler

Because a handler takes `IMediatorExceptionContext` rather than `MediatorContext`, a test that only checks the translation logic needs no DI container, no service provider and no real mediator - mock or fake the interface directly:

```csharp
[Fact]
public async Task Handle_UniqueConstraintViolation_ReportsFriendlyMessage()
{
    var sut = new SqlExceptionHandler();
    var exception = new SqlException(number: 2601);
    var context = Substitute.For<IMediatorExceptionContext>();

    await sut.Handle(exception, context);

    context.Received(1).SetHandled("This record already exists.");
}
```

A hand-written fake works just as well as a mocking library, since the interface's surface is small enough to implement in a few lines.

A handler that does touch `context.Context` - one reading or writing the pipeline `MediatorContext`, e.g. to call `AddError` directly or to read `Depth`/`Features` - still needs no container: build the `MediatorContext` with `MediatorContext.Create(...)` and pass it to a real `MediatorExceptionContext`, the same way the library's own boundary does.

```csharp
var mediatorContext = MediatorContext.Create(new CreateOrderCommand());
var context = new MediatorExceptionContext(exception, mediatorContext);

await sut.Handle(exception, context);

// what the handler wrote to the pipeline context itself, e.g. via context.Context.AddError(...)
Assert.Contains("This record already exists.", mediatorContext.ErrorMessages);
```

See [Unit-test a custom middleware](6.-Pipelines-and-Middlewares.md#how-to-unit-test-a-custom-middleware) for what `MediatorContext.Create` fills in and where it draws the line.

### Migrating from a catch-all `ErrorHandlingMiddleware`

The usual pre-existing pattern is a middleware at the start of the pipeline that catches exceptions and converts each one into a message via `AddError`. It is no longer needed for the *safety* it provided (the boundary now guarantees nothing leaks) and it is no longer the right place for the *translation* it did, because a middleware catching an exception hides it from the boundary - and therefore from `ExecuteUnhandled` callers and from the boundary's logging.

Port it branch by branch:

| Existing code | Replacement |
|---|---|
| `catch (SomeException e) { context.AddError("..."); }` | `IMediatorExceptionHandler<SomeException>` calling `context.SetHandled("...")` with the same message |
| `catch (Exception e) { context.AddError(e.Message); }` | delete it - this is the default the boundary now applies, minus the message leak. If you cannot migrate every caller at once, [`LegacyExceptionMessageHandler`](#restore-the-pre-safe-by-default-message-behavior-temporarily) restores the old behavior as a stopgap |
| `catch (Exception e) { logger.LogError(e, ...); throw; }` | delete it - the boundary already logs the original exception at Error. Keep it (or [`UseExceptionLogging`](6.1.-Ready-to-use-middlewares.md#useexceptionlogging-exceptionloggingmiddleware)) only if you need the log entry to include middleware-specific context, or if you want failures of `*Unhandled` calls logged too |
| a validation middleware short-circuiting with `AddError(...)` | keep `AddError` when the message is written for the user; switch to `AddException` when the caller should get a typed exception from `ExecuteUnhandled` |

The `Pipaslot.Mediator.Analyzers` package (bundled with `Pipaslot.Mediator`, no separate install) flags a remaining broad `catch (Exception)` - or bare `catch` - inside a class implementing `IMediatorMiddleware` that guards a call to `next` and neither rethrows nor calls `context.AddException(e)`, as build warning `PIPMED001`, linking back to this section. The pattern shown above (`catch` + `AddException`, no rethrow) is exempt - it does not have the message-leak problem the warning targets.

Then review the rest of the application:

- **Root-level `*Unhandled` call sites**: no translation happens there by contract. If such a call site is the boundary of an HTTP endpoint or a background job, it needs its own `try/catch` - or should switch to `Execute`/`Dispatch`.
- **Alerting rules**: `MediatorUnhandledErrorException` is logged at Warning and is no longer an "unexpected error". If you alert on it, hook the Warning level explicitly instead of relying on Error.
- **Tests asserting on error messages**: assertions expecting `Exception.Message` in a failed `Response` now need either a registered handler or an assertion against the generic message.

### Restore the pre-safe-by-default message behavior temporarily

Porting every call site to a typed handler in one change is not always realistic. `LegacyExceptionMessageHandler` is a ready-to-use, opt-in `IMediatorExceptionHandler<Exception>` that reports every otherwise-untranslated exception's own `Exception.Message` to the client, the same way a `catch (Exception e) { context.AddError(e.Message); }` middleware did before safe-by-default existed:

```csharp
services.AddMediator()
    .AddExceptionHandler<LegacyExceptionMessageHandler>()
    ...
```

Because it is registered for `Exception`, it also becomes the catch-all for every exception type that has no more specific handler - [resolution](#resolution-rules) always picks the most specific registered type for the thrown exception, so a handler you register for a narrower type still wins over this one regardless of registration order.

**This re-opens the exact leak [safe-by-default](#safe-by-default) exists to close.** `Exception.Message` routinely contains connection strings, file paths, SQL fragments, or entity identifiers, and in [Client-Server usage](8.-HTTP-transport-and-configuration-for-Client-Server-usage.md) that message is serialized straight to a browser. Treat this handler as a temporary bridge while you migrate callers that depended on the old behavior, not as a permanent fixture - replace it with typed `IMediatorExceptionHandler<TException>` registrations for the specific exception types you actually want to translate as soon as you can, and remove it once none are left relying on it.
