Don't you like the names [Request](2.-Core-concepts-and-glossary.md#request) and [Message](2.-Core-concepts-and-glossary.md#message)? Or do you want to provide more action types to cover your specific pipeline behavior? Just define your own [Action](2.-Core-concepts-and-glossary.md#action) types by implementing the marker interface `IMediatorAction` (or `IMediatorAction<TResult>` for actions with a result).
Here is an example of naming for CQRS (Command and Query Responsibility Segregation).

ICommand.cs
```
using Pipaslot.Mediator.Abstractions;

namespace CustomMediator.Cqrs
{
    /// <summary>
    /// Marker type for actions and pipelines
    /// </summary>
    public interface ICommand : IMediatorAction
    {
    }
}
```

ICommandHandler.cs (optional)
```
using Pipaslot.Mediator.Abstractions;

namespace CustomMediator.Cqrs
{
    public interface ICommandHandler<TCommand> : IMediatorHandler<TCommand> where TCommand : ICommand
    {

    }
}
```

IQuery.cs
```
using Pipaslot.Mediator.Abstractions;

namespace CustomMediator.Cqrs
{
    /// <summary>
    /// Base interface for actions
    /// </summary>
    public interface IQuery<TResult> : IQuery, IMediatorAction<TResult>
    {
    }
    /// <summary>
    /// Marker type for pipelines
    /// </summary>
    public interface IQuery : IMediatorAction
    {
    }
}
```

IQueryHandler.cs (optional)
```
using Pipaslot.Mediator.Abstractions;

namespace CustomMediator.Cqrs
{
    public interface IQueryHandler<TQuery, TResult> : IMediatorHandler<TQuery, TResult> where TQuery: IQuery<TResult>
    {

    }
}

```

And that is it. Easy!

The custom handlers do not have to be implemented. It will also work even if you inherit only from `IMediatorHandler`. We are using them just as a naming convention.

Now, just create inherited actions and handlers to meet your business needs. And don't forget to use [Pipelines](2.-Core-concepts-and-glossary.md#pipeline) and [Middlewares](2.-Core-concepts-and-glossary.md#middleware) to boost your solution.

It is not mandatory to define custom handlers. It is beneficial only in case you need to work with the `TCommand` and `TQuery` together with a custom abstraction.

## When not to bother
Custom action/handler marker types are a naming/organization convenience, not a functional requirement - plain `IMediatorAction`/`IMediatorHandler` already run everything described elsewhere in this wiki. Consider skipping this if:
- Your app only has a handful of actions, where CQRS-style Command/Query naming wouldn't add clarity over the built-in [Request](2.-Core-concepts-and-glossary.md#request)/[Message](2.-Core-concepts-and-glossary.md#message) names.
- You don't need a dedicated [pipeline](6.-Pipelines-and-Middlewares.md#pipeline-types) for the new marker type - the built-in [action-specific pipeline](6.-Pipelines-and-Middlewares.md#action-specific-pipeline) already matches `IRequest`/`IMessage`, so a custom marker only pays off once you need a *different* pipeline for a subset of actions.
- Introducing another interface layer just to rename concepts would confuse newcomers to the codebase more than the plain `Request`/`Message` naming would.
