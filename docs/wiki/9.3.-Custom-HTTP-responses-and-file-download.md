Use this chapter when a handler needs to return something other than the mediator's default aggregated JSON response — most commonly, a file download triggered by an HTTP GET request.

Since Version 6.0.0, the mediator detects if the response has already started. By default, the mediator starts writing JSON responses with all results aggregated during processing. There might be cases when another response is needed. For example, when the mediator is executed via a GET request and a file download is expected. In such a case, you can inject `IHttpContextAccessor` and write your own response in a handler or in a middleware.

## File download (via HTTP GET)
From NuGet: **Pipaslot.Mediator.Http** since version **5.0.0**

In previous versions, the mediator supported only HTTP POST requests. This made file download complicated through HTML links/anchors.
[Mediator](2.-Core-concepts-and-glossary.md#mediator) exposes a service `IMediatorUrlFormatter` to make the URL building as easy as possible. This service is registered by configuring the client mediator via `services.AddMediatorClient()`. You only need to inject this service and pass the action instance to get a formatted URL.

```
@inject Pipaslot.Mediator.Http.IMediatorUrlFormatter _mediatorUrlFormatter
<a href="@_mediatorUrlFormatter.FormatHttpGet(new MyFileDownloadAction(FileId))">Download</a>
```

**WARNING:** This approach is not recommended for accessing sensitive files in applications using authentication through request headers (for example, JWT). In the case of links/anchors, the headers are not handed over to the server, which causes a loss of authentication and authorization.

**NOTE:** Keep in mind that the URL query has a limited size depending on your server configuration. We do not recommend sending a large amount of data via the action, like long texts or templates used for file rendering.

## Handler implementation (recommended: `IMediatorHttpResult`)

Once the URL is formatted, you need to expose the file in the HTTP response. The recommended way is to have the handler return a plain data object implementing `Pipaslot.Mediator.Http.IMediatorHttpResult`. `MediatorMiddleware` applies it directly to the HTTP response, in place of its default JSON body, after the [pipeline](2.-Core-concepts-and-glossary.md#pipeline) has completed:

```
public class FileDownloadResult(string fileName, string content) : IMediatorHttpResult
{
    public Task ApplyAsync(HttpContext httpContext, CancellationToken cancellationToken)
    {
        //Without this header, the file download does not pop up in the browser.
        httpContext.Response.Headers["Content-Disposition"] = $"attachment;filename={fileName}.txt";
        httpContext.Response.ContentType = "text/plain";
        return httpContext.Response.WriteAsync(content, cancellationToken);
    }
}

public class MyFileDownloadActionHandler : IMediatorHandler<MyFileDownloadAction, FileDownloadResult>
{
    public Task<FileDownloadResult> Handle(MyFileDownloadAction action, CancellationToken cancellationToken)
    {
        return Task.FromResult(new FileDownloadResult(action.FileName, "Hello world!"));
    }
}
```

This is why the pattern is preferred over writing to `HttpContext.Response` directly: the handler stays plain data, with no `IHttpContextAccessor`/`IMediatorContextAccessor` dependency and no manual root-vs-nested check. A [nested call](5.-Mediator-API.md#access-mediator-context-from-services) never leaks its `IMediatorHttpResult` into the response of the actual root action automatically — it is only applied if the calling handler explicitly returns it (or forwards it) as its own result, so a handler used both as a root action and as a nested call behaves correctly either way, without any extra guard. At most one `IMediatorHttpResult` is allowed in the root result set. If more than one is found, `MediatorMiddleware` throws a `MediatorHttpException` rather than silently applying one and discarding the rest — treat this as a configuration bug (e.g. a handler forwarding a nested `IMediatorHttpResult` it should have wrapped or discarded instead).

The implementation owns and is responsible for disposing of any resources (streams, etc.) it holds.

## Alternative: writing to `HttpContext.Response` directly

You can also inject `IHttpContextAccessor` and write your own response in a handler or in a middleware. This gives you low-level control over `HttpContext`, but you lose the safety `IMediatorHttpResult` gives you for nested calls — you have to guard it yourself.

**WARNING:** Only write to `HttpContext.Response` when the handler is executing as the root HTTP call. A handler can also run as a [nested call](5.-Mediator-API.md#access-mediator-context-from-services) triggered by another handler's own `IMediator.Execute`/`Dispatch`. `MediatorMiddleware` decides whether to write its own JSON response purely by checking `HttpContext.Response.HasStarted` — it does not know *which* handler wrote to the response. A nested handler that writes to `HttpContext.Response` unconditionally will silently replace the response intended for the actual root action, with no exception raised. Guard the write with [`Context`](2.-Core-concepts-and-glossary.md#context)`.IsNested`, obtained through `IMediatorContextAccessor`, so the handler only touches the HTTP response when it is genuinely the one driving the request.

```
public class MyFileDownloadActionHandler(IHttpContextAccessor httpContextAccessor, IMediatorContextAccessor mediatorContextAccessor) : IMediatorHandler<MyFileDownloadAction>
{
    public async Task Handle(MyFileDownloadAction action, CancellationToken cancellationToken)
    {
        if (mediatorContextAccessor.Context?.IsNested == true)
        {
            throw new InvalidOperationException($"Action {nameof(MyFileDownloadAction)} writes directly to the HTTP response and must not be executed as a nested call.");
        }
        var httpContext = httpContextAccessor.HttpContext;
        if (httpContext == null)
        {
            throw new InvalidOperationException($"Action {nameof(MyFileDownloadAction)} can be used only for request over HTTP.");
        }
        var fileContent = "Hello world!"
        //Without this header, the file download does not pop up in the browser.
        httpContext.Response.Headers["Content-Disposition"] = $"attachment;filename={action.FileName}.txt";
        httpContext.Response.ContentType = "text/plain";
        await httpContext.Response.WriteAsync(fileContent, cancellationToken);
    }
}
```
