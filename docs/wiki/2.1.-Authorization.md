_Introduced since version 6.2.0, but custom policy rules are fully supported since 7.0.0_

[Mediator](2.-Core-concepts-and-glossary.md#mediator) authorization is Policy-based. Every policy defines one or more rules which are verified against user identity. It is possible to define your own policies by implementing the `IPolicy` interface, or you can use the built-in `IdentityPolicy` and policy attributes.

The class `IdentityPolicy` uses the standard `ClaimPrincipal` identity available at runtime. That provides basic capabilities to verify authentication status, role, or claim existence.
You can combine policies defined on actions and handlers. If multiple policies are defined, then the user must meet all of them (there is an AND condition connecting all the policies).

# Policies defined on Actions
You can enforce authorization policies directly on action classes or their interfaces by applying policy attributes. This approach ensures that only users meeting specific criteria can execute the associated actions.

For example, to restrict an action to authenticated users:
```
[AuthenticatedPolicy]
public class SampleAction : IMediatorAction<SampleResponse>
{
    // Action implementation
}
```
To restrict an action to users with a specific role:
```
[RolePolicy("Admin")]
public class AdminAction : IMediatorAction<AdminResponse>
{
    // Action implementation
}
```
These attributes and interfaces ensure that the Mediator enforces the specified policies before executing the action.

The authorization can be enforced at the action level by implementing the IActionAuthorization interface. This allows you to define custom authorization logic that applies to specific actions.
That may be useful when you need to define a custom policy from the incoming data. For example, vertical slicing authorization depending on the combination of primary keys.

# Policies defined on Handlers
Alternatively, you can define authorization policies and attributes on action handlers. You can use it if you prefer to have policies defined on backend handlers rather than on shared contracts.
```
[AuthenticatedPolicy]
public class SampleActionHandler : IMediatorHandler<SampleAction, SampleResponse>
{
    public Task<SampleResponse> Handle(SampleAction action, CancellationToken cancellationToken)
    {
        // Handler implementation
    }
}
```
For more control over authorization, you can enforce policies at the handler level using the IHandlerAuthorization or IHandlerAuthorizationAsync interfaces.

# Synchronous Authorization Using IHandlerAuthorization
For handlers where authorization can be determined synchronously:
```
public class SampleAction : IMediatorAction<SampleResponse> { }

public class SampleActionHandler : IMediatorHandler<SampleAction, SampleResponse>, IHandlerAuthorization<SampleAction>
{
    public IPolicy Authorize(SampleAction action)
    {
        return IdentityPolicy.Authenticated()
    }
}
```
## Asynchronous Authorization Using IHandlerAuthorizationAsync
If authorization requires an external data source (e.g., checking user roles in a database), use IHandlerAuthorizationAsync:
```
public class SampleActionHandler(IDataService dataService) :  IMediatorHandler<SampleAction, SampleResponse>, IHandlerAuthorizationAsync<SampleAction>
{
    public async Task<IPolicy> AuthorizeAsync(SampleAction action, CancellationToken cancellationToken))
    {
        var areaId = await dataService.GetAreaId(action.Id, cancellationToken);

        return new AreaMembershipPolicy(areaId);//Custom policy verifying if the user is member of the area where the data belongs
    }
}
```

## Policies counting with the actual model state (conditional access)
Every `Rule` carries a `RuleScope`:
* `RuleScope.State` (default) — the outcome depends on the current model/entity state and can change over time, e.g. "is the current user the owner of this record". Any rule you derive from action data should keep this default.
* `RuleScope.Identity` — the outcome only depends on the user's identity (role/claim/authentication) and cannot change during a session. `IdentityPolicy` tags all of its built-in rules this way.

This distinction lets client-server scenarios know whether an authorization result may be cached for the whole session or must be re-evaluated per request: if every rule that contributed to a decision is `Identity`-scoped, the result can be reused safely, but if any rule is `State`-scoped, it depends on data that can change and must be re-checked.

Conditional access based on model state is expressed by inspecting the *actual stored record*, not the incoming action payload. An action's fields come from the client and cannot be trusted for an ownership check - always load the record from your data source using only its identifier and compare the value that is actually persisted. Use `IHandlerAuthorizationAsync<TAction>` for this, since loading the record requires an external data source:
```
public class SampleActionHandler(IDataService dataService, IUserIdentity user) : IMediatorHandler<SampleAction, SampleResponse>, IHandlerAuthorizationAsync<SampleAction>
{
    public async Task<IPolicy> AuthorizeAsync(SampleAction action, CancellationToken cancellationToken)
    {
        var record = await dataService.GetRecordAsync(action.Id, cancellationToken);

        return Rule.AllowOrDeny(record.OwnerId == user.Identity.Id, "Is the owner of this resource", "Must be the owner of this resource");
    }
}
```

# Authorization setup
The authorization is enforced by applying the authorization mediator middleware via `.UseAuthorization()`.

The mediator can check, during application startup, whether all actions or their handlers have at least one policy defined. If not, it fails directly. To enable the check, set the `checkExistingPolicies` parameter for the mediator middleware registered in the .NET Core pipeline:
`app.UseMediator(checkExistingPolicies: true);`

**!!! IMPORTANT !!!:** When introducing authorization on existing projects, ensure that every action or its handler has at least one policy specified. 
In case of actions where authorization shouldn't be applied, set the `AnonymousPolicyAttribute` on the [Action](2.-Core-concepts-and-glossary.md#action) class or its interface.

## Ignore authorization for specific pipeline
Authorization is enforced by adding the Authorization middleware to the default or any specific pipeline. The mediator contains a service that detects actions and handlers missing any policy, to prevent keeping open doors in your application. This checker is activated on the application builder by using `app.UseMediator(true, true)`. Unfortunately, this service is not able to detect which pipeline will be applied, as it can be decided based on action data at runtime. This checker will throw exceptions in case some policy is missing and the checker is allowed. To prevent this, you have to explicitly define which actions and their handlers should be ignored by this checker, as in the following example: `app.UseMediator(true, new []{typeof(MyPolicylessAction)})`

## Client-side authorization for Client-Server usage
The mediator is designed to always fetch Authentication and Authorization status from the server in case of Client-Server usage. The mediator itself cannot guarantee that all policies will be correctly evaluated for all possible authorization scenarios.
You can implement your own authorization middleware and place it in your client project. But then you have to resolve how to hand over the user identity to the client and how to evaluate handler validations if they are defined as well.

# Exceptions
The mediator authorization produces two kinds of exceptions: AuthorizationException and AuthorizationRuleNotMetException. 

AuthorizationException is a general exception used to indicate that an authorization failure has occurred. It typically signals that the user does not meet the necessary criteria to execute an action or access a handler.

When is it thrown?
* When an action or handler requires authorization, but the user is unauthorized.
* When the authorization check fails due to missing policies or an invalid security context.

AuthorizationRuleNotMetException is more specific, and it inherits from AuthorizationException. It is thrown when an explicit authorization rule is evaluated and fails. It differs from AuthorizationException in that it indicates that a particular rule was expected to be met but was not.

When is it thrown?
* When a policy explicitly checks conditions (e.g., role membership, resource ownership) and the conditions are not satisfied.
* When implementing custom policies that enforce business logic authorization.

## Custom error message formatted with IRuleFormatter 
`IRuleFormatter` and its default `DefaultRuleFormatter` were removed in version 8 and replaced by `INodeFormatter` / `DefaultNodeFormatter` (`Pipaslot.Mediator.Authorization.Formatting`). Instead of formatting one `IRule` at a time, the new formatter converts a whole reduced tree of nodes (`IRecursiveNode`) into a single user-friendly message:
```
public interface INodeFormatter
{
    public string Format(IRecursiveNode rootNode);
}
```
It is used both to build the `AuthorizationRuleNotMetException` message and to fill `AuthorizeRequestResponse.Reason` for client-side "can I do this?" queries.

`AddMediator(...)` registers `DefaultNodeFormatter` with a plain `services.AddScoped<INodeFormatter, DefaultNodeFormatter>()`. Adding another `services.AddScoped<INodeFormatter, MyCustomNodeFormatter>()` afterwards does **not** remove that registration - it adds a second one, and both remain in the container (e.g. `IEnumerable<INodeFormatter>` would resolve both). It still works for the typical case because a single-instance resolution (constructor injection via `GetService<INodeFormatter>()`) returns the *last* registered implementation, but it's not a true replacement. To actually replace the registration, use `Replace` (`Microsoft.Extensions.DependencyInjection.Extensions`):
```
services.AddMediator(...);
services.Replace(ServiceDescriptor.Scoped<INodeFormatter, MyCustomNodeFormatter>());
```
Because most of `DefaultNodeFormatter`'s methods are `protected virtual`, a small message tweak doesn't require a full reimplementation:
```
public class MyNodeFormatter : DefaultNodeFormatter
{
    public MyNodeFormatter() => NegativeOutcomeMessagePrefix = "Access refused: ";
}
```
registered the same way with `Replace`.

# Custom rules
There is no abstract `Rule` base class to inherit from - `Rule` is a concrete class constructed via factory methods (`Rule.Allow`, `Rule.Deny`, `Rule.Unavailable`, `Rule.AllowIf`, `Rule.DenyIf`, `Rule.UnavailableIf`, `Rule.AllowOrDeny`, `Rule.DenyOrAllow`). A fully custom rule is instead implemented by writing your own `IPolicy`:
```
public interface IPolicy
{
    public Task<RuleSet> Resolve(IServiceProvider services, CancellationToken cancellationToken);
}
```
A custom policy only needs to resolve a `RuleSet` built from one or more `Rule` instances, optionally pulling in services from DI:
```
public class AreaMembershipPolicy : IPolicy
{
    private readonly int _areaId;
    public AreaMembershipPolicy(int areaId) => _areaId = areaId;

    public Task<RuleSet> Resolve(IServiceProvider services, CancellationToken cancellationToken)
    {
        var currentUser = services.GetRequiredService<IIdentityAccessor>(); // your own service
        var isMember = currentUser.IsMemberOfArea(_areaId);
        var set = new RuleSet(Rule.AllowOrDeny(isMember, "Is member of area", $"Must be a member of area {_areaId}"));
        return Task.FromResult(set);
    }
}
```
This custom policy can then be attached the same way as `IdentityPolicy` or `AreaMembershipPolicy` shown above - via `IActionAuthorization`, `IHandlerAuthorization<TAction>`, or `IHandlerAuthorizationAsync<TAction>`. A custom policy can also be packaged as its own attribute by implementing `IPolicy` directly on an `Attribute` class, the same way `AnonymousPolicyAttribute`, `AuthenticatedPolicyAttribute`, and `RolePolicyAttribute` do.

## Rule outcome (Unavailable, Deny, Allow, Ignored)
Every `Rule` resolves to one `RuleOutcome`:
```
public enum RuleOutcome
{
    Deny = 0,        // User can not perform the operation
    Allow = 1,       // User can perform the operation
    Unavailable = 2, // The operation shouldn't be available/shown to the user
    Ignored = 3      // The rule should be skipped
}
```
* **Deny** - the default outcome, also applied when no rule was defined at all.
* **Allow** - the user may perform the operation.
* **Unavailable** - a stronger negative than `Deny`: the operation/feature shouldn't even be shown/offered to the user, as opposed to merely being refused. When reducing a `RuleSet`, an `Unavailable` outcome always wins over `Allow` or `Deny`, regardless of the operator used to combine the rules.
* **Ignored** - the rule doesn't apply and contributes nothing to the decision. For example, `Rule.AllowIf(condition, reason)` resolves to `Ignored` when `condition` is `false`. Under the `Add`/`Or` operators an ignored rule is simply skipped; under `And` it is treated as blocking, since AND requires every rule to affirmatively `Allow`.

`RuleOutcome` is ultimately collapsed into the coarser `AccessType` enum (`Deny`/`Allow`/`Unavailable`), which is what `PolicyResolver` and `AuthorizeRequestHandler` act on to decide whether to throw `AuthorizationRuleNotMetException`.

## Operators + & |
`Rule` and `RuleSet` can be combined with three operators, each mapping to a `RuleSet` `Operator`:
* `+` (`Operator.Add`) - combines rules/rule sets without requiring all of them to agree; ignored rules are simply skipped.
* `&` (`Operator.And`) - all combined rules/rule sets must resolve to `Allow`.
* `|` (`Operator.Or`) - at least one combined rule/rule set must resolve to `Allow`.
```
IPolicy mustOwnAndBeAuthenticated = ownershipRule & IdentityPolicy.Authenticated();
IPolicy adminOrOwner = IdentityPolicy.Role("Admin") | ownershipRule;
```
The same `&`/`|` operators are also defined on `IPolicy` itself (and on `Policy`, the AND/OR combinator over whole policies), so entire policies - not just individual rules - can be composed the same way:
```
IPolicy isOwner = new AreaMembershipPolicy(areaId);
IPolicy isAdmin = IdentityPolicy.Role("Admin");

IPolicy adminOrOwner = isAdmin | isOwner;
IPolicy combined = Policy.And(isOwner, IdentityPolicy.Authenticated());
```
Combining policies this way builds a nested tree of `RuleSet`s that `RuleSet.Reduce()` folds into a single `RuleOutcome`, which `INodeFormatter` then turns into a human-readable message. For `adminOrOwner` denied on both sides, the message reads `"Role 'Admin' is required. OR Must be a member of area 5"` - note that the outermost combination is never wrapped in parentheses; `DefaultNodeFormatter` only wraps a sub-expression in parentheses when it combines *multiple* rules and is itself being joined with a sibling expression, e.g. `"(Sentence1 OR Sentence2) AND Sentence3"`.

### Reason text convention
A custom rule's reason text is passed through to `INodeFormatter` verbatim, for whichever outcome it resolved to - unlike built-in named rules (`Role`, `Claim`, `Authentication`), where the formatter ignores the supplied value and synthesizes its own fixed message (e.g. always rendering `"Role 'X' is required."` on Deny). Since nothing rephrases custom reason text for you, word it according to the outcome it belongs to, so that messages combined with `AND`/`OR` read as one uniform sentence:
* **Reason behind a positive outcome (Allow)** - state the fact that holds true, e.g. `"Is member of area"`. Often left empty, since a successful check rarely needs explaining.
* **Reason behind a negative outcome (Deny, Unavailable)** - state the requirement needed to pass, phrased as an actionable statement, e.g. `"Must be a member of area 5"`, matching how built-in rules phrase failures (`"Role 'Admin' is required."`, `"User has to be authenticated."`).
